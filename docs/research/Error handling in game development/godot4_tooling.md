# Godot 4 (up to 4.7) error-handling, logging, crash-reporting and testing toolchain

Status: complete (researched 2026-10-03; latest Godot stable = 4.7.2, latest sentry-godot = 2.3.0).

Context for the report writer: these notes feed a plan for a Godot 4.7, GDScript-only (standard, non-.NET), Compatibility-renderer, single-player idle/business sim with local JSON saves in `user://`, Android first + Windows. The project already (a) counts errors in headless tests with `class _ErrorCounter extends Logger` + `OS.add_logger()`, (b) uses `push_error`/`push_warning` in GameData/Economy, (c) gates a dev panel behind `OS.is_debug_build()`. "Source-verified" means I read the engine C++ source on GitHub myself (`master`, Oct 2026); the key GDScript-VM release-path lines (`#define GD_ERR_BREAK(m_cond)` empty, `*dst = src->get(*index, &valid);`, default-return on error) and the `debug_features` line in SConstruct were re-checked on the **`4.7` branch** and are identical. "Experiment" means I ran a probe script on the locally installed Godot 4.7.2 editor binary.

## 1. GDScript language level: no exceptions — what you get instead, and what a runtime error does

### Takeaway
GDScript has no try/catch; the idiom is (1) functions that can fail return an `Error` code (or null/empty) that the caller checks, (2) `push_error`/`push_warning` to report, (3) `assert` for programmer-only checks that vanish in release exports. A runtime script error in the editor/debug build prints an error, pauses in the debugger (editor only), aborts the current function and returns a default value; in a **release export the GDScript VM skips most of those checks entirely**, so the bad line yields `null` and execution silently continues with no error printed.

### Cited Findings
- `assert()`: "For performance reasons, the code inside assert() is only executed in debug builds or when running the project from the editor"; "When running from the editor, failed asserts also cause a debugger break"; on failure it generates an error and returns a default value from the current method; `assert` is a keyword, not a function, so it cannot be used as a Callable or inside expressions — [@GDScript class ref (latest/4.7)](https://docs.godotengine.org/en/latest/classes/class_@gdscript.html)
- 4.7 class XML, verbatim: "Don't include code that has side effects in an [method assert] call. Otherwise, the project will behave differently when exported in release mode"; assert "can be used as a stronger form of push_error for reporting errors to project developers or add-on users" — [@GDScript.xml (4.7)](https://github.com/godotengine/godot/blob/4.7/modules/gdscript/doc_classes/@GDScript.xml); an older forum case shows exactly this trap — [Godot Q&A (old)](https://forum.godotengine.org/58684/godot-error-message-whle-exporting)
- `print_debug()` adds the current stack frame "when running with the debugger turned on"; for `get_stack()`, `print_stack()` and `print_debug()` the 4.7 XML notes: "By default, backtraces are only available in editor builds and debug builds. To enable them for release builds as well, you need to enable `debug/settings/gdscript/always_track_call_stacks`" — [@GDScript.xml (4.7)](https://github.com/godotengine/godot/blob/4.7/modules/gdscript/doc_classes/@GDScript.xml)
- Logging doc: `printerr()`, `push_error()` and `push_warning()` write to standard error; stderr "is always flushed on every print, even in projects exported in release mode", while plain stdout in release exports "is only flushed when the project exits or crashes to improve performance" (`application/run/flush_stdout_on_print`, default `false`, `.debug` override `true`) — [Logging tutorial (latest)](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html); defaults from [ProjectSettings ref](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html)
- **Source-verified (gdscript_vm.cpp, master):** at the end of `GDScriptFunction::call`, inside `#ifdef DEBUG_ENABLED`, a script error calls `_err_print_error(..., ERR_HANDLER_SCRIPT)`, then `GDScriptLanguage::get_singleton()->debug_break(err_text, false)`, then sets `retvalue = _get_default_variant_for_data_type(return_type)` — i.e. the function stops at the bad line and returns the type's default (0, "", null...) to the caller, which keeps running — [gdscript_vm.cpp](https://github.com/godotengine/godot/blob/master/modules/gdscript/gdscript_vm.cpp)
- **Source-verified:** in the same file, `GD_ERR_BREAK(m_cond)` expands to nothing without `DEBUG_ENABLED`; `OPCODE_GET_KEYED` in release does `*dst = src->get(*index, &valid);` and never looks at `valid`; the `err.error != CALL_OK` check after a method call (e.g. calling a method on null or with wrong arguments) is inside `#ifdef DEBUG_ENABLED`. So in a release export, `dict["missing_key"]` or `null_obj.method()` produce `null` and the next line runs, with no message — [gdscript_vm.cpp](https://github.com/godotengine/godot/blob/master/modules/gdscript/gdscript_vm.cpp)
- **Source-verified:** `DEBUG_ENABLED` is defined only for `target=editor` and `target=template_debug` (`env.debug_features = env["target"] in ["editor", "template_debug"]`), not for `template_release` — [SConstruct](https://github.com/godotengine/godot/blob/master/SConstruct)
- Engine-side (C++) errors (e.g. `JSON.parse_string` failure) and `push_error`/`push_warning` are still reported in release templates — source-verified, see section 3 ([error_macros.h](https://github.com/godotengine/godot/blob/master/core/error/error_macros.h), [variant_utility.cpp](https://github.com/godotengine/godot/blob/master/core/variant/variant_utility.cpp))
- **Experiment (this machine, Godot 4.7.2.stable editor binary, `--headless -s probe.gd`):** `d["missing"]`, `null_obj.get_class()` and `var i: int = d["missing"]` each printed `SCRIPT ERROR: ...` with `at: <func> (res://probe.gd:<line>)` and a "GDScript backtrace (most recent call first)" block; each function stopped at that line and returned `""` (the String default) to the caller, which carried on; `push_error` printed `ERROR: explicit push_error / at: push_error (core/variant/variant_utility.cpp:1023)` plus a GDScript backtrace; `JSON.parse_string("{bad json")` printed `ERROR: Parse JSON failed. Error at line 0: Expected key` and returned null; `assert(bump())` ran its side effect once (editor). The same probe could **not** be run on the 4.7.2 debug/release export templates because Windows Application Control ("An Application Control policy has blocked this file") blocks those unsigned binaries on this PC — so the release-template behaviour above rests on source reading only. (Probe script: scratchpad `relprobe/probe.gd`, not in the project.)
- Forum (Godot 4.6.2, May 2026): asked how to catch errors from dynamically loaded GDScript, the blunt community answer was "You don't" — there is no catching mechanism — [Godot Forum: How to catch errors thrown by GDScript objects?](https://forum.godotengine.org/t/how-to-catch-errors-thrown-by-gdscript-objects/138519)

### Inferences
- The project's existing `_ErrorCounter` approach works because tests run on the editor binary (`DEBUG_ENABLED`). The same Logger in a **release** export would NOT see most GDScript runtime errors (bad key, null call, wrong arg count) — only engine-reported errors, `push_error`/`push_warning`, and things like failed file/JSON calls. So "zero errors in the release log" does not mean "no script bugs": playtest builds for testers should be **debug exports** (or a release export with explicit `push_error` at important checkpoints).
- Release builds being "silent and keep going" means a hidden bug can corrupt data (e.g. a null value gets written into the save). Save-writing code should validate what it writes (explicit `if` checks + `push_error`), not rely on runtime errors or `assert`.
- Never put work inside `assert(...)` — only pure checks.

### Gaps
- I did not test the exact behaviour of typed variables receiving `null` in release builds (e.g. `var n: int = dict["missing"]`); the VM source suggests checks are skipped, but the resulting value was not verified by running a release export.
- (Resolved: `JSON.parse_string()` failure prints an engine error in all build types — source-verified in section 3.)

## 2. Logger class, OS.add_logger(), ScriptBacktrace

### Takeaway
`Logger` + `OS.add_logger()` / `OS.remove_logger()` and `ScriptBacktrace` arrived in **Godot 4.5** (PR #91006, Mikael Hermansson / Juan Linietsky). Both virtual methods can be called from any thread at the same time (use a `Mutex`), you cannot print/push_error from inside them (recursion), and stack frames are only filled in release exports when `debug/settings/gdscript/always_track_call_stacks` is enabled.

### Cited Findings
- `Logger` (RefCounted): enum `ErrorType` — `ERROR_TYPE_ERROR = 0`, `ERROR_TYPE_WARNING = 1`, `ERROR_TYPE_SCRIPT = 2`, `ERROR_TYPE_SHADER = 3` — [Logger class ref (latest)](https://docs.godotengine.org/en/latest/classes/class_logger.html)
- Virtuals: `_log_error(function: String, file: String, line: int, code: String, rationale: String, editor_notify: bool, error_type: int, script_backtraces: Array[ScriptBacktrace])` and `_log_message(message: String, error: bool)` (`error` true = meant for stderr). Both: "This method will be called from threads other than the main thread, possibly at the same time, so you will need to have some kind of thread-safety in your implementation of it, like a Mutex." — [Logger class ref](https://docs.godotengine.org/en/latest/classes/class_logger.html)
- Script backtraces in `_log_error` contain frames only in editor/debug builds by default; enable `debug/settings/gdscript/always_track_call_stacks` for release; they "will not contain any captured variables" (capture yourself with `Engine.capture_script_backtraces(include_variables)`) — [Logger class ref](https://docs.godotengine.org/en/latest/classes/class_logger.html)
- Logging tutorial: "To avoid infinite recursion, you cannot effectively use `print()` and its related methods in `_log_message()`. You also can't effectively use `push_error()` or `push_warning()` in `_log_error()`." Register the logger "typically in an autoload's `_init()` method"; the official minimal example is `class CustomLogger extends Logger` with both methods, then `OS.add_logger(CustomLogger.new())` — [Logging tutorial (latest)](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html)
- "Since Godot 4.5, when GDScript code encounters an error, it will log a backtrace that points to the origin of the error, while also containing the call stack leading to it"; always on in editor/debug exports, off by default in release "for performance" — [Logging tutorial](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html)
- Godot 4.5-stable was published 2025-09-15 (GitHub release); 4.6-stable 2026-01-26; 4.7-stable 2026-06-18 — [GitHub API: godot releases](https://api.github.com/repos/godotengine/godot/releases/tags/4.5-stable). PR #91006 "Add `Logger` and ability to print and log script backtraces", milestone 4.5 — [PR #91006](https://github.com/godotengine/godot/pull/91006)
- Godot 4.5 release page: "Script backtracing, gives developers the exact details on where an issue happened in the code. Even in 'Release' builds"; "Custom loggers allow developers to intercept log messages and errors. That makes it possible to create a tool for reporting bugs within your game"; reminder to enable *Debug > Settings > GDScript > Always Track Call Stacks*; PR [#91006](https://github.com/godotengine/godot/pull/91006) — [Godot 4.5 release page](https://godotengine.org/releases/4.5/)
- `ScriptBacktrace` (RefCounted): `get_frame_count()`, `get_frame_file(i)`, `get_frame_function(i)`, `get_frame_line(i)`, `get_language_name()`, `is_empty()`, `format(indent_all, indent_frames)`, plus global/local/member variable getters (only filled if captured with `include_variables`); warning that storing captured variable Variants keeps objects alive — [ScriptBacktrace class ref](https://docs.godotengine.org/en/latest/classes/class_scriptbacktrace.html)
- Project settings: `debug/settings/gdscript/always_track_call_stacks` default `false`; `debug/settings/gdscript/always_track_local_variables` default `false` — [ProjectSettings ref](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html)
- `OS.add_logger(logger: Logger)` / `OS.remove_logger(logger: Logger)` — [OS class ref](https://docs.godotengine.org/en/latest/classes/class_os.html)
- Community how-to thread for 4.5+ exists — [Godot Forum: How to use the new Logger class in Godot 4.5+](https://forum.godotengine.org/t/how-to-use-the-new-logger-class-in-godot-4-5/127006)
- **Experiment (4.7.2 editor binary, Logger registered in a headless SceneTree script) — where the message text arrives:** for GDScript runtime errors `error_type` was `2` (SCRIPT), `file/line/function` pointed at the script (`res://probe.gd:30`, `bad_key`), and **`rationale` was empty** (the text is in `code`); for `push_error("...")` `error_type` was `0`, `file` was `core/variant/variant_utility.cpp:1023`, `function` was `push_error`, `rationale` was **empty** and the text was in `code`, with the script location only in `script_backtraces` (1 frame, top `res://probe.gd:58`); for `JSON.parse_string` failure the text *was* in `rationale` (`Parse JSON failed. Error at line 0: Expected key`) with `file` = `core/io/json.cpp:629`. This matches the source: VM script errors call `_err_print_error(func, file, line, err_text, false, ERR_HANDLER_SCRIPT)` and `ERR_PRINT(msg)` passes the message as the "error" (code) argument, while `*_MSG` macros pass condition + message separately — [gdscript_vm.cpp](https://github.com/godotengine/godot/blob/master/modules/gdscript/gdscript_vm.cpp), [error_macros.h](https://github.com/godotengine/godot/blob/master/core/error/error_macros.h). The official tutorial example's comment "The error text is in `rationale`" is therefore only true for some errors — [Logging tutorial](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html)

### Inferences
- Any Logger that displays or stores messages should use `var text := rationale if not rationale.is_empty() else code`, and for location prefer the top `script_backtraces` frame when `file` starts with `core/`/`scene/` (C++). The project's existing `_ErrorCounter` only counts, so it is unaffected.
- Thread safety matters for this project: Godot's own resource loading, audio and rendering can log from worker threads. A Logger that appends to an Array (ring buffer for an in-game overlay) must lock a `Mutex` around the append, and must not touch UI nodes directly — hand the data to the main thread (e.g. `call_deferred`, or poll the buffer in `_process` of the overlay).
- Uses that extend the current test-only `_ErrorCounter`: (1) an autoload `ErrorLog` that keeps the last N errors in memory and shows a red badge/overlay in debug builds; (2) writes errors + backtrace (`ScriptBacktrace.format()`) to its own `user://logs/errors.txt` that survives on Android where built-in file logging is off by default; (3) attaches the last N lines to a "Report a bug" button. Turning on `always_track_call_stacks` in the shipped build costs some performance (doc says it's off "for performance"), but for an idle sim with light scripting it is likely affordable — measure first.
- Because release builds skip most GDScript runtime error checks (section 1), a Logger in a release build mostly sees engine errors and explicit `push_error`/`push_warning` calls — so explicit `push_error` at key validation points is what makes the release-build Logger useful.

### Gaps
- No official statement on the exact performance cost of `always_track_call_stacks` in release.
- Not verified whether `OS.add_logger()` called in an autoload's `_init()` catches errors raised by *earlier* autoloads (load order); presumably only errors after registration are seen.

## 3. Error-code convention, error_string(), FileAccess/JSON error reporting

### Takeaway
Engine APIs that can fail return an `Error` enum value (`OK` = 0) or a null/empty value plus a "last error" getter; `error_string(code)` turns the code into readable text. For JSON, use the `JSON` instance API (`parse()` + `get_error_line()`/`get_error_message()`) when you need to show *where* a file is broken; `JSON.parse_string()` just returns `null` and prints an engine error.

### Cited Findings
- **Source-verified:** `error_string(Error)` returns the name from the internal `error_names` table, or `"(invalid error code)"` for out-of-range values — [variant_utility.cpp](https://github.com/godotengine/godot/blob/master/core/variant/variant_utility.cpp)
- `JSON.parse(json_text, keep_text=false)` returns an `Error`; on success the result is in `data`; on failure use `get_error_line()` ("Returns 0 if the last call to parse() was successful, or the line number where the parse failed") and `get_error_message()`; static `JSON.parse_string()` "Returns null if parse failed" — [JSON class ref (latest)](https://docs.godotengine.org/en/latest/classes/class_json.html)
- **Source-verified:** `JSON::parse_string` is `ERR_FAIL_COND_V_MSG(error != Error::OK, Variant(), vformat("Parse JSON failed. Error at line %d: %s", ...))` — so it does print line + message as an engine error (visible to a Logger, in all build types) and returns null — [json.cpp](https://github.com/godotengine/godot/blob/master/core/io/json.cpp)
- JSON has only one number type: `stringify` "will convert all numerical values to float types" — relevant for save files where ints come back as floats — [JSON class ref](https://docs.godotengine.org/en/latest/classes/class_json.html)
- **Source-verified:** the engine's `ERR_FAIL_*`/`ERR_PRINT`/`WARN_PRINT` macros are not wrapped in `DEBUG_ENABLED` (only `DEV_ASSERT` is compiled out, under `DEV_ENABLED`), so engine-side errors are reported in release export templates too — [error_macros.h](https://github.com/godotengine/godot/blob/master/core/error/error_macros.h)
- **Source-verified:** `push_error(...)` is implemented as `ERR_PRINT(join_string(...))` and `push_warning(...)` as `WARN_PRINT(...)`, so they work in all builds and reach a Logger as `ERROR_TYPE_ERROR` / `ERROR_TYPE_WARNING` (not `ERROR_TYPE_SCRIPT`) — [variant_utility.cpp](https://github.com/godotengine/godot/blob/master/core/variant/variant_utility.cpp)
- **Source-verified:** `ERR_PRINT` is `_err_print_error(FUNCTION_STR, __FILE__, __LINE__, m_msg)`, i.e. the `function/file/line` passed to `Logger._log_error` for a `push_error` call are the **C++** location (`core/variant/variant_utility.cpp`), not the GDScript line; the GDScript location is in the `script_backtraces` argument, which the engine fills on every error via `ScriptServer::capture_script_backtraces(false)` — [error_macros.h](https://github.com/godotengine/godot/blob/master/core/error/error_macros.h), [error_macros.cpp](https://github.com/godotengine/godot/blob/master/core/error/error_macros.cpp)

### Inferences
- A custom Logger that wants "which script line called push_error" must read `script_backtraces[0].get_frame_file(0)` / `get_frame_line(0)` (when non-empty); in release builds this is empty unless `always_track_call_stacks` is on. For GDScript runtime errors (`ERROR_TYPE_SCRIPT`, debug builds only) the `file/line` args already point to the script.
- The project's existing pattern (`push_warning("Couldn't write the save: %s" % error_string(FileAccess.get_open_error()))`) is the idiomatic Godot 4 pattern. For data files, switching GameData from `parse_string` to a `JSON` instance would let messages name the line of a broken `data/*.json` file (parse_string already prints it to the log, but the code can't show it in-game).

### Gaps
- Not checked: exactly which `Error` codes `FileAccess.open()` sets on Android storage failures.

## 4. Built-in file logging and where logs live

### Takeaway
Godot writes its own log file (`user://logs/godot.log`, rotating, 5 files kept) **only on desktop by default** (`enable_file_logging=false`, `enable_file_logging.pc=true`). On Android nothing is written to a file unless the developer enables it, and even then the file sits in private app storage that a player can't browse — so player reports need an in-game "copy/send log" feature.

### Cited Findings
- Defaults: `debug/file_logging/enable_file_logging` = `false`; `debug/file_logging/enable_file_logging.pc` = `true`; `debug/file_logging/log_path` = `"user://logs/godot.log"`; `debug/file_logging/max_log_files` = `5` — [ProjectSettings ref (latest)](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html)
- "By default, logs are written to `user://logs/godot.log` on desktop platforms"; "Up to 5 log files are kept by default"; crash logs go to the same file but need debug symbols for usable backtraces — [Logging tutorial](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html); `--log-file <file>` "Write output/error log to the specified path instead of the default location defined by the project" — [Command line tutorial](https://docs.godotengine.org/en/latest/tutorials/editor/command_line_tutorial.html)
- Other output settings: *Application > Run > Disable stdout / Disable stderr* (runtime: `Engine.print_to_stdout`, `Engine.print_error_messages`), `debug/settings/stdout/verbose_stdout` (default `false`; `print_verbose()` only prints when on), `application/run/flush_stdout_on_print` (`false`; `.debug` = `true`) — [Logging tutorial](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html), [ProjectSettings ref](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html)
- `user://` on Windows: `%APPDATA%\Godot\app_userdata\[project_name]`; with `application/config/use_custom_user_dir` + `custom_user_dir_name`: `%APPDATA%\[custom_user_dir_name]`. On mobile `user://` is "unique to the project and is not accessible by other applications for security reasons" — [Data paths (latest)](https://docs.godotengine.org/en/latest/tutorials/io/data_paths.html)
- Android `user://` maps to the app's private internal storage (`/data/data/<package>/files/...`); developers can reach it with `adb shell` then `run-as <package>` on debuggable builds (community source, not official docs) — [Godot Forums thread 39160](https://godotforums.org/d/39160-can-i-directly-access-files-saved-on-android-to-user)
- `OS.get_user_data_dir()` returns the absolute `user://` path; `OS.shell_show_in_file_manager(path)` "is currently only implemented on Windows and macOS"; `OS.shell_open(uri)` opens with the OS default handler — [OS class ref](https://docs.godotengine.org/en/latest/classes/class_os.html)

### Inferences
- For this project: either add the override `debug/file_logging/enable_file_logging.android = true` (the `.tag` override syntax works with any feature tag, per the feature-tags doc in section 10) or, better, write a small own error log through the existing Logger approach — controls size and content, works the same on PC and Android.
- Player-facing on PC: an "Open log folder" button (`OS.shell_show_in_file_manager(OS.get_user_data_dir() + "/logs")`). On Android: copy recent log lines to the clipboard (`DisplayServer.clipboard_set`) or include them in an in-app bug report; asking players to use adb is unrealistic.
- Because release-build stdout is buffered until exit, `print()` lines just before a crash can be lost; diagnostics that matter should use `printerr`/`push_warning` (stderr, flushed every time) or a custom Logger that flushes its own file.

### Gaps
- I found no official Godot doc page stating the Android `user://` absolute path; only forum sources.

## 5. Crash handling (native crashes), debug symbols, Android crashes

### Takeaway
Godot's built-in crash handler prints a native backtrace to stderr/the log on desktop, but official export templates have no debug info, so the backtrace is mostly addresses unless you build your own templates with symbols. Since 4.5 the official GitHub releases ship **native debug symbols for Android** (`template_release.android`) — upload them to Google Play Console or use `ndk-stack`. Native crashes are rare for a GDScript-only game; script bugs are the main failure mode.

### Cited Findings
- Crash backtraces "print to standard error when crashes occur" and "require debugging symbols to be useful"; header text set by `debug/settings/crash_handler/message` (default "Please include this when reporting the bug to the project developer.") and `.editor` variant — [Logging tutorial](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html), [ProjectSettings ref](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html)
- `--disable-crash-handler` "Disable crash handler when supported by the platform code"; `OS.crash(message)` "should *only* be used for testing the system's crash handler" — [Command line tutorial](https://docs.godotengine.org/en/latest/tutorials/editor/command_line_tutorial.html), [OS class ref](https://docs.godotengine.org/en/latest/classes/class_os.html)
- **Verified via GitHub API:** release assets include `Godot_native_debug_symbols.<ver>.stable.template_release.android.zip` (and `.editor.android.zip`) for 4.5-stable (published 2025-09-15), 4.5.1, 4.6 (2026-01-26) and 4.7 (2026-06-18); 4.4.1 had none; no Windows/desktop symbol packages are listed — [GitHub API: 4.7-stable release](https://api.github.com/repos/godotengine/godot/releases/tags/4.7-stable)
- Android crash guide: official symbols from GitHub releases or custom build with `scons platform=android target=template_release debug_symbols=yes separate_debug_symbols=yes generate_android_binaries=yes`; symbolicate with `ndk-stack -sym path/to/native_debug_symbols/arm64-v8a/ -dump crash.txt`; Play Console upload at *Test and release > Latest releases and bundles > (bundle) > Downloads > Assets > Native debug symbols* — [Resolving crashes on Android (latest)](https://docs.godotengine.org/en/latest/tutorials/platform/android/resolving_crashes_on_android.html)
- Sentry: "official Godot Engine builds only provide templates without debug information files"; readable native stacks need self-compiled templates with symbols — [Sentry: Readable Stack Traces (Godot)](https://docs.sentry.io/platforms/godot/configuration/stack-traces)
- Latest Godot stable when writing: **4.7.2-stable, 2026-08-18** (4.7.1 on 2026-07-14; 4.6.3 on 2026-05-20) — [GitHub releases API](https://api.github.com/repos/godotengine/godot/releases)

### Inferences
- Android-first solo dev: upload the official Android native symbols zip for the exact Godot version to Play Console with each release — free, no custom builds, gives readable native crash stacks in Android Vitals. Windows native stacks would need custom templates; probably not worth it here.
- Google Play's Android Vitals (crashes + ANRs) works for any Play-published app with no SDK — a free baseline for native crashes; it never sees GDScript errors (those don't crash the game).

### Gaps
- Did not verify the exact Android logcat tag Godot uses, nor the desktop crash-handler output format in 4.7.

## 6. GDScript warnings, static typing, and the editor's error/debugger panels (incl. Android remote debug)

### Takeaway
Every GDScript warning is a project setting under `debug/gdscript/warnings/` with level Ignore (0) / Warn (1) / Error (2); setting a warning to Error stops the script compiling, which is Godot's "treat warnings as errors" (per warning, no single global switch). The type-safety warnings (`untyped_declaration`, `unsafe_*`) are **off by default**; turning them on is the cheapest compile-time bug prevention available to a GDScript project. 4.6 added `directory_rules` (replacing `exclude_addons`) and the `missing_await` warning; 4.7 added `confusable_temporary_modification`.

### Cited Findings
- **Verified in the class-reference XML of each branch:** `debug/gdscript/warnings/exclude_addons` exists in 4.4 and 4.5; 4.6 replaces it with `debug/gdscript/warnings/directory_rules` (default `{ "res://addons": 0 }`, PR [#93889](https://github.com/godotengine/godot/pull/93889), milestone 4.6) and adds `missing_await` (default 0, PR [#107936](https://github.com/godotengine/godot/pull/107936)); 4.7 adds `confusable_temporary_modification` (default 1, PR [#118002](https://github.com/godotengine/godot/pull/118002)); 4.5 removed `constant_used_as_function`, `function_used_as_property`, `property_used_as_function`. `onready_with_cast` exists only on `master` (post-4.7) — [ProjectSettings.xml 4.6](https://github.com/godotengine/godot/blob/4.6/doc/classes/ProjectSettings.xml), [4.7](https://github.com/godotengine/godot/blob/4.7/doc/classes/ProjectSettings.xml), [master](https://github.com/godotengine/godot/blob/master/doc/classes/ProjectSettings.xml)
- `directory_rules`: "the GDScript parser chooses the most specific rule, i.e. the most nested directory containing the script. If the decision is **Exclude**, warnings are not generated"; "It is not recommended to remove or change the rule for "res://addons"" — [ProjectSettings.xml (master)](https://github.com/godotengine/godot/blob/master/doc/classes/ProjectSettings.xml)
- Defaults (master/4.7 XML): `debug/gdscript/warnings/enable` = `true`; `untyped_declaration` = 0 ("when a variable or parameter has no static type, or if a function has no static return type"; recommended together with editor setting `text_editor/completion/add_type_hints`); `inferred_declaration` = 0 (for `:=`); `unsafe_property_access`, `unsafe_method_access`, `unsafe_cast`, `unsafe_call_argument` = 0; `integer_division` = 1; `unused_variable` = 1; `get_node_default_without_onready` = 2 — [ProjectSettings.xml (master)](https://github.com/godotengine/godot/blob/master/doc/classes/ProjectSettings.xml)
- Warning docs: warnings "won't prevent the game from running, but you can turn them into errors"; ignore one line with `@warning_ignore("unused_variable")` (names match the project-setting names) or a region with `@warning_ignore_start` / `@warning_ignore_restore`; Advanced Settings must be on to see the section — [GDScript warning system (latest)](https://docs.godotengine.org/en/latest/tutorials/scripting/gdscript/warning_system.html)
- Static typing: "With static typing, GDScript can detect more errors without even running the code"; typed code uses "optimized opcodes"; the script editor turns a line number green when the line is type-safe; typed collections `Array[int]`, `Dictionary[String, int]` — [Static typing in GDScript (latest)](https://docs.godotengine.org/en/latest/tutorials/scripting/gdscript/static_typing.html)
- Typed dictionaries are a **Godot 4.4** feature: **verified** — `Dictionary.is_typed()` is absent from the 4.3 class XML and present in 4.4 — [Dictionary.xml 4.3](https://github.com/godotengine/godot/blob/4.3/doc/classes/Dictionary.xml) vs [4.4](https://github.com/godotengine/godot/blob/4.4/doc/classes/Dictionary.xml); gdtoolkit added support in 4.3.2 (Oct 2024) — [gdtoolkit CHANGELOG](https://github.com/Scony/godot-gdscript-toolkit/blob/master/CHANGELOG.md)
- Debugger panel: the **Errors** tab is "where error and warning messages are printed while running the game"; other tabs: Stack Trace, Evaluator, Profiler, Visual Profiler, Network Profiler, Monitors, Video RAM, Misc — [Debugger panel (latest)](https://docs.godotengine.org/en/latest/tutorials/scripting/debug/debugger_panel.html)
- `push_error` "does not pause project execution. To print an error message and pause project execution in debug builds, use `assert(false, "test error")` instead"; `print_rich` doc recommends `push_error`/`push_warning` over print for problems because they also show a stack trace — [@GlobalScope.xml (4.7)](https://github.com/godotengine/godot/blob/4.7/doc/classes/@GlobalScope.xml)
- One-click deploy: with an Android preset marked Runnable and USB debugging on, Godot can "automatically export, install and run the project (in debug mode) on the device"; wireless via `adb pair <ip address>:<port>` — [One-click deploy (latest)](https://docs.godotengine.org/en/latest/tutorials/export/one-click_deploy.html). *Debug > Deploy with Remote Debug*: "using one-click deploy will make the executable attempt to connect to this computer's IP so the running project can be debugged"; *Keep Debug Server Open* lets externally started sessions connect — [Overview of debugging tools (latest)](https://docs.godotengine.org/en/latest/tutorials/scripting/debug/overview_of_debugging_tools.html)
- 4.6 editor: errors/warnings in the Output panel have a clickable file part (PR [#108473](https://github.com/godotengine/godot/pull/108473)) and source errors can open in an external editor (PR [#111805](https://github.com/godotengine/godot/pull/111805)); script debugger got a Step Out button and ObjectDB snapshots — [Godot 4.6 release page](https://godotengine.org/releases/4.6/)

### Inferences
- For a solo non-coder working with an AI assistant, setting `untyped_declaration`, `unsafe_property_access`, `unsafe_method_access`, `unsafe_call_argument` (and maybe `unsafe_cast`) to **Error** turns many would-be release-build silent failures (section 1) into "won't compile" errors that the existing `tests/check_project.gd` compile check already catches in headless runs. Expect a one-off cleanup cost (JSON data is `Variant`, so dictionary reads need explicit casts / typed locals). A middle path: set them to Warn first and fix gradually.
- `missing_await` (4.6+) is worth enabling at Warn if the game uses `await` for timers/tweens.
- One-click deploy + Remote Debug gives the Android device's script errors in the editor's Errors tab with the same debug-build behaviour as on PC — the main "see errors on the phone" workflow during development.

### Gaps
- (Resolved in section 9: `--check-only` does return a failure exit code in 4.7, source-verified.)
- The Debugger panel doc doesn't describe the Stack Trace pane's error-break toggles; not verified for 4.7.

## 7. Sentry's official Godot SDK and alternatives

### Takeaway
`getsentry/sentry-godot` is a mature, MIT-licensed C++ GDExtension (current **2.3.0, 2026-09-29**) that needs **Godot 4.5+** for SDK 1.x/2.x, supports Windows/Linux/macOS/Android/iOS (+Web since 1.4.0) and works with plain GDScript (C# optional since 2.0.0). It captures native crashes plus Godot errors through its own Logger, with breadcrumbs, log/scene-tree/screenshot attachments, a ready-made user-feedback form, throttling, and `before_send` filtering. Android export **requires the Gradle build**. Free Developer plan: 5k errors/month, 1 user.

### Cited Findings
- Architecture: "Built as a C++ GDExtension library using mature Sentry SDKs like sentry-native as the foundation"; compatibility: SDK `1.x`/`2.x` → "Godot 4.5 or later", `0.x` → "Godot 4.3 or later"; platforms: Windows/Linux/macOS (x86_64, x86_32, arm64), Android (arm64, arm32, x86_64, x86_32), iOS (device + simulator), Web "supported in 1.4.0 and later", C#/.NET "supported in 2.0.0 and later"; MIT — [sentry-godot README](https://github.com/getsentry/sentry-godot)

### Inferences
- **Important interaction with section 1:** Sentry's Godot error capture is Logger-based. In a *release* export, the GDScript VM does not raise most script runtime errors at all (source-verified), so Sentry will mostly see `push_error`/`push_warning`, engine (C++) errors and native crashes — not "null access on line 42". To get script-error reports from testers, ship testers a **debug export** (Sentry environment `export_debug`) or add explicit `push_error` checks. Not verified by experiment; should be tested before relying on it.
- Fit for this project: technically a good fit (GDScript-only, 4.7, Android + Windows). Costs: Android Gradle build (needs Android build template + full Android SDK setup), a privacy policy / consent text for sending crash data (GDPR), and the free tier's single user. Reasonable to defer until there are external testers; a local error log + "copy log" button covers solo testing.
- Compatibility renderer: the SDK is a GDExtension unrelated to the renderer; I found no statement either way. Screenshot capture may behave differently per renderer — unverified.

## 10. Debug vs release exports: what changes for errors

### Takeaway
Debug exports (`template_debug`, `DEBUG_ENABLED`) behave like the editor for script errors (reported, function aborted) except there's no editor to break into; release exports skip `assert`, skip most GDScript runtime checks, buffer stdout, and only carry GDScript call stacks if `always_track_call_stacks` is on. Use `OS.is_debug_build()` / feature tags to gate dev tools, and export filters to keep dev-only files out of release packages.

### Cited Findings
- `OS.is_debug_build()`: true for a debug export template or the editor, false for a release template; use `OS.has_feature("template")` to check "exported at all" — [OS.xml (4.7)](https://github.com/godotengine/godot/blob/4.7/doc/classes/OS.xml)
- Feature tags: `debug`, `release`, `editor`, `editor_hint`, `editor_runtime`, `template`, platform tags (`android`, `windows`, `mobile`, `pc`, `web`...); project settings can be overridden per tag (`setting.debug`), read with `ProjectSettings.get_setting_with_override()`; custom export-preset tags are "**not used** when running the project from the editor" — [Feature tags (latest)](https://docs.godotengine.org/en/latest/tutorials/export/feature_tags.html)
- Export preset Resources tab: a filter to include non-resource files and a filter "to exclude every file of a certain type" — [Exporting projects (godot-docs master)](https://github.com/godotengine/godot-docs/blob/master/tutorials/export/exporting_projects.rst)
- Release stdout is only flushed at exit/crash "to improve performance", stderr always flushed — [Logging tutorial](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html)
- `debug/settings/gdscript/always_track_call_stacks`: "Whether GDScript call stacks will be tracked in release builds, thus allowing `Engine.capture_script_backtraces` to function"; no effect in editor/debug builds. `always_track_local_variables`: costs "roughly 50 bytes of memory per local variable, for every compiled class in the entire project, so can be several MiB in larger projects" — [ProjectSettings.xml (master)](https://github.com/godotengine/godot/blob/master/doc/classes/ProjectSettings.xml)
- Community reports of games "not working correctly if exported with debug disabled" with no error output — [Godot Forums 28137](https://godotforums.org/d/28137-android-game-not-working-correctly-if-exported-with-debug-is-disabled) (older, likely Godot 3)

### Inferences
- `OS.is_debug_build()` gating keeps the dev panel from *running* in release, but its files are still packed unless excluded with an export filter (e.g. exclude `scenes/debug/*` in the release preset) — and then nothing may `preload()` them, only `load()` behind the gate. The project's check script already enforces the gate.
- Side observation: on the developer's own Windows 11 PC, Windows Application Control blocked the official (unsigned) 4.7.2 export-template executables from running (see section 1 experiment). Exported Windows builds of the game are made from those templates, so they may be blocked the same way on this PC (and on players' PCs with Smart App Control on) unless code-signed — worth checking before relying on Windows release-build testing. (Observation only; the policy's exact source was not investigated.)
- Test on a **release** export on a real Android device before shipping, since release silently tolerates errors that debug reports — a bug can "work" differently in release (e.g. an `assert` with side effects).

### Gaps
- No measured numbers found for the per-call cost of `print()` in release exports beyond the buffering note.

## 11. What's new in Godot 4.6 / 4.7 for errors, logging, debugging

### Takeaway
The big feature (Logger + script backtraces) is 4.5. In 4.6/4.7 the Logger/ScriptBacktrace/OS/Engine APIs are **unchanged** (only doc clarifications); additions are editor/debugger conveniences and warnings: 4.6 — clickable Output errors, open errors in external editor, Step Out, ObjectDB snapshots, tracing-profiler support, `directory_rules`, `missing_await`; 4.7 — `confusable_temporary_modification` warning, Perfetto default tracing on Android, Linux crash-trace symbol improvements, Android Play-Store crash fixes.

### Cited Findings
- **Verified by diffing class XML between the `4.5` and `4.7` branches:** no method/member additions in `OS`, `Engine`, `EngineDebugger`, `@GDScript`, `@GlobalScope`; `Logger`/`ScriptBacktrace` only gained doc text (Mutex wording; "Logging errors from this method using functions like push_error or push_warning is not supported...
