# How game developers handle errors during development (engine-agnostic)

Context for the report writer: these notes feed a plan for a solo developer with no prior coding experience, building a single-player, data-driven (JSON) business/idle sim with AI help, local JSON saves, Android + PC, MMO backend planned years later. "SOLO-FIT" marks practices that suit that situation especially well; "BIG-TEAM" marks practices whose cost only pays off with many people. Godot-specific APIs are deliberately left out (another researcher covers them).

Source-quality note: primary sources used are official engine docs (Epic/Unreal, Unity, Android), studio blogs (Factorio/Wube, Riot, Hutch, PlayStation Blog on Croteam), Noel Llopis' blog, Robert Nystrom's *Game Programming Patterns*, and the Google C++ Style Guide. Some breadcrumb/ring-buffer material comes only from bugnet.io, a crash-reporting vendor's blog (marketing-adjacent, unsigned articles) and from AccelByte vendor docs; treat those as "common practice as described by vendors", not studio evidence.

## 1. Assertion philosophy: fail fast vs. log and continue, tiered checks, what gets stripped

### Takeaway
The established pattern is *tiered* checks: hard "halt now" asserts for programmer mistakes that make further execution meaningless, plus soft "report once and keep running" checks for problems that are wrong but survivable, with both aimed at programmers and mostly compiled out of the shipped game. Content/user mistakes (designers, data files, players) are a separate category that should be reported clearly rather than crash the game.

### Cited Findings
- **Unreal's three families.** `check`/`checkf` halt execution when the expression is false; `checkNoEntry()` halts if unreachable code is reached; `checkNoReentry()` halts if run more than once; `checkNoRecursion()` halts on recursion; `unimplemented()` halts if a must-override virtual is called — [Epic: Asserts in Unreal Engine](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)
- **Unreal `check` is stripped and its expression is not evaluated** when checks are disabled: checks run in Debug and Development by default; "Slow" variants (`checkSlow`) only in Debug; `USE_CHECKS_IN_SHIPPING=1` re-enables them in Test/Shipping. Epic's doc: "A key feature of `assert` is that it doesn't exist in shipping code, meaning it has no performance impact on a shipped product, but also must not have any side effects." — [Epic: Asserts](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)
- **Unreal `verify` exists precisely for side effects**: "Verify macros evaluate their expressions even in builds where Check macros are disabled", so a call like "do the thing and return success" still happens in shipping — [Epic: Asserts](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)
- **Unreal `ensure` = non-fatal, report-once.** "If an Ensure macro's expression evaluates as false, the Engine will inform the crash reporter, but will continue running." "In order to avoid flooding the crash reporter, Ensure macros will only report once per Engine or Editor session." `ensureAlways`/`ensureAlwaysMsgf` report every time. Ensure expressions are evaluated in all builds, but only contact the crash reporter in Debug, Development, Test and Shipping Editor builds — [Epic: Asserts](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)
- **Unity**: methods of `UnityEngine.Assertions.Assert` are "only conditionally included in a Development Build or if the ManagedCodeVariant is set to Checked or Debug" (via the `UNITY_ASSERTIONS` define), i.e. stripped from release builds; current docs say Assert throws an exception on failure and, if a debugger is attached, an `AssertionException` pauses execution to invoke the debugger — [Unity: Assertions.Assert](https://docs.unity3d.com/ScriptReference/Assertions.Assert.html). Older Unity docs describe `Debug.Assert` as logging an error message to the Unity console on failure — [Unity 2018.1 legacy docs: Debug](https://docs.unity.cn/2018.1/Documentation/ScriptReference/Debug.html)
- **Noel Llopis (Games From Within, 3 Oct 2005)**: asserts are "a message from the programmers to the programmers and nobody else"; the key distinction is *programming errors* (developers misusing code) vs *user errors* (content creators or players misusing tools/game). Asserts detect bugs immediately, document a function's assumptions, and act as reminders that "This code doesn't even handle this situation" (an agile trade-off instead of bomb-proofing everything). He accepts asserts disappearing from release builds (no programmers there to debug), embraces asserts as "exploding comments", and recommends writing your own assert macro so the team controls behaviour (log, email, throw, or show a dialog) — [Llopis: Asserting Oneself](https://gamesfromwithin.com/asserting-oneself/)
- **Steve Rabin, "Squeezing More Out of Assert"**, is a chapter in the first *Game Programming Gems* (pp. 109–114), reprinted as section 1.4 of *Best of Game Programming Gems* — [lighthouse3d GPG series index](https://www.lighthouse3d.com/2011/05/game-programming-gems-series/); [Graphics and Game Gems Database](https://gameenginegems.com/gemsdb/book.php?id=3). (Contents of the chapter not verified — see Gaps.)
- **Halt vs. fall back is an explicit design trade-off.** *Game Programming Patterns* (Service Locator chapter): asserting a service exists means "Users don't need to handle a missing service" and initialization bugs surface immediately, but can block a large team; a null fallback "lets us keep running the game even when a service isn't there" but makes it "harder to debug an *unintentionally* missing service". Nystrom suggests the null-service route mainly for larger teams — [Nystrom: Service Locator](https://gameprogrammingpatterns.com/service-locator.html)

### Inferences
- The modern consensus maps cleanly to three severities: (1) **fatal** — internal state is corrupt, stop now (Unreal `check`); (2) **non-fatal but must be seen** — log loudly once, keep playing (Unreal `ensure`); (3) **diagnostic** — compiled out or silenced in release. Unreal's split between "stripped, no side effects" (`check`) and "always evaluated" (`verify`/`ensure`) is the clearest documented statement of *why* side effects in asserts are dangerous.
- "Report once" (ensure) is the industry answer to the playtest problem where an assert in a per-frame loop either spams thousands of lines or forces the tester to click "ignore" forever.
- SOLO-FIT: a solo dev is both the programmer and the "content creator", so Llopis's split still matters but is about *where the mistake lives* (code vs JSON data vs save file vs player input), not who made it. For an idle/business sim, internal invariants (negative stock, money NaN, job finishing before it started) deserve fatal-in-dev checks; data typos deserve validation messages (section 4); player/save problems must never crash (repair or migrate).
- SOLO-FIT: with an AI assistant writing code, asserts double as executable documentation of assumptions that the AI (and future-you) can't otherwise see; "exploding comments" fire when a later AI edit breaks an assumption.
- For a game that keeps running for a long time (offline catch-up, idle loops), a fatal check in a development build costs little (you're watching), while in a release build the same failure should degrade gracefully and be logged — matching the debug-vs-release split all engines use.

## 2. Logging: channels, verbosity, files, ring buffers, log-once, structured logs, good messages

### Takeaway
Mature engines log through named categories with ordered verbosity levels, always write to a file as well as an on-screen/console view, let verbosity be raised per category at runtime, and increasingly support structured (named-field) logs. A rolling in-memory buffer of recent lines/"breadcrumbs" attached to crash reports is standard practice in crash-reporting tooling.

### Cited Findings
- **Unreal categories**: built-in categories plus custom ones declared per system/module (`DECLARE_LOG_CATEGORY_EXTERN` / `DEFINE_LOG_CATEGORY`) — [Epic: Logging in Unreal Engine](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Unreal verbosity ladder** (7 levels): Fatal ("Always prints a fatal error to the console and log file, then crashes"), Error (commandlets mark the run as failed), Warning, Display, Log ("Prints a message to the log file, however, it does not print to the console"), Verbose, VeryVerbose — [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Compile-time + runtime control**: verbosity set at compile time per category, changeable at runtime via command line (`-LogCmds="LogCategory VerbosityLevel"`) or console (`log LogCategory verbose`) — [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Always to file**: "Logs are saved in a `.txt` file in your project's `Saved/Logs` directory", in addition to the editor Output Log — [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Structured logging**: `UE_LOGFMT` (Unreal 5.2+) supports positional or named parameters — [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **"Errors" as a failure signal for automation**: in Unreal, an Error-level log causes commandlets (headless/CI tools) to be marked as failures — [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Report-once to avoid flooding**: Unreal's ensure reports only once per session "to avoid flooding the crash reporter" — [Epic: Asserts](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)
- **Per-system logging without littering code**: a decorator ("LoggedAudio") wraps a service and "logs each sound call", so logging for one subsystem can be switched on/off — [Nystrom: Service Locator](https://gameprogrammingpatterns.com/service-locator.html)
- **Ring buffers / breadcrumbs (vendor descriptions)**: breadcrumbs are "a chronological trail of recent events stored in an in-memory ring buffer — typically the last 20 to 50 events", attached to crash reports; recommend also keeping the last ~50–500 log lines in a ring buffer and attaching them automatically — [bugnet.io: breadcrumbs](https://bugnet.io/blog/how-to-add-breadcrumbs-to-your-games-crash-reports); [bugnet.io: player logs](https://bugnet.io/blog/how-to-use-player-logs-to-debug-game-issues); breadcrumb feature also documented by [AccelByte Blackbox docs](https://docs.accelbyte.io/development-toolkit/developer-guides/blackbox-error-reporter/breadcrumbs/). Vendor guidance: log meaningful state changes (scene loads, key actions, transitions) and keep a "current state" context alongside the trail — [bugnet.io: custom game events for crash context](https://bugnet.io/blog/using-custom-game-events-for-crash-context)

### Inferences
- Good-practice checklist distilled from the above: one category per system (e.g. Economy, Save, Data, Jobs); a fixed severity ladder where "Error" means *a bug or broken data*, never routine flow; Verbose/debug lines off by default; every line timestamped and written to a file that survives a crash; repeated warnings collapsed ("log once" or "log once per key"); messages that name *what* (which building/resource id), *where* (file/field), *expected vs actual*, and *what the game did about it* (e.g. "used 0, skipped recipe").
- SOLO-FIT: a session log file plus a small ring buffer of recent lines is cheap and is the main way a solo dev diagnoses a bug reported from an Android phone they can't attach a debugger to. Logging state *transitions* (job started/finished, offline catch-up computed N seconds, save loaded vN→migrated) rather than per-frame values keeps logs readable.
- SOLO-FIT: structured fields (id=..., amount=...) make logs greppable now and machine-readable later when the MMO backend needs server-side log aggregation.
- Making "Error" mean "fail the automated run" (as Unreal commandlets do) is a cheap way to turn logs into a test signal: a headless test that finishes with any error-level line counts as failed.

## 3. Making errors impossible to miss during play-testing (overlays, toasts, consoles, debug HUDs)

### Takeaway
Engines provide on-screen debug messaging and in-game consoles so problems surface while playing rather than hiding in a log nobody reads; the documented primitives are on-screen colored messages with a duration, runtime-adjustable logging from a console, and "report once" so a visible error does not drown the screen.

### Cited Findings
- **Unreal on-screen messages**: `GEngine->AddOnScreenDebugMessage()` displays temporary overlays with customizable duration and color, using the same format specifiers as logs — [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Unreal in-game console** can change log verbosity per category at runtime (`log LogCategory verbose`) — [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Unreal Data Validation results** surface in the editor's Message Log (and console output in CI), not buried in a text file — [Epic: Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)
- **Ensure failures go to the crash reporter while the game keeps running** (Development/Test builds), i.e. non-fatal problems are still *collected* rather than only printed — [Epic: Asserts](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)
- **Unity Assert pauses into the debugger when one is attached** (AssertionException) — [Unity: Assertions.Assert](https://docs.unity3d.com/ScriptReference/Assertions.Assert.html)
- A Unity forum thread is titled "Assertion errors silent in development build", illustrating the common failure mode where assert failures only go to a log that no one watches on device — [Unity Discussions](https://discussions.unity.com/t/assertion-errors-silent-in-development-build/944051) (thread title only; content not fetched)

### Inferences
- A standard indie pattern (cheap, SOLO-FIT): in debug builds only, show a small persistent red badge/counter "3 errors, 12 warnings" in a screen corner that opens the recent-log view when tapped, plus a brief toast the *first* time each distinct error happens. This combines the on-screen message idea with report-once, and works on a phone where there is no editor console.
- A developer console / debug panel (cheat money, skip time, force offline catch-up of N hours, reload data files, dump state) is high-value for an idle sim because time-based bugs are otherwise slow to reproduce. Keep it in debug-only code so it can't ship (matches the project's existing `scenes/debug/` + `OS.is_debug_build()` rule).
- BIG-TEAM: automatic upload of every ensure/assert to a central crash/triage server with deduplication is the large-studio version; for a solo dev, the local log file + on-screen counter gives most of the benefit.

### Gaps
- No primary sources fetched for specific shipped-game examples (e.g. Quake/Source developer consoles, Bethesda console, studio "red screen" assert overlays, Naughty Dog/Insomniac debug menus). These are well known in the industry but unverified in this research pass; don't cite specifics without a source.

## 4. Content / data validation (build-time and load-time)

### Takeaway
Studios treat data files as code that needs checking: validators run automatically on save, on demand, and headless in CI, and report errors at the exact asset/field. The trend reported by a mobile studio (Hutch) is to centralize *all* validation in one place at import time so the person who made the typo sees the error immediately.

### Cited Findings
- **Unreal Data Validation plugin**: validates assets against custom rules; common uses "Checking that assets meet name conventions" and "Enforcing space and performance budgets". Runs **on save** (default on), **on demand** (editor menus/Content Browser), and **headless in CI** (`UnrealEditor-Cmd.exe <Project>.uproject -run=DataValidation`) — [Epic: Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)
- **How Unreal validators are written**: either an asset class overrides `IsDataValid`, or a separate `UEditorValidatorBase` (C++, Blueprint or Python) implements `CanValidateAsset`/`ValidateLoadedAsset`, which "must call `AssetPasses` or `AssetFails` for each of its execution paths" (no silent outcomes). Failures appear in the Message Log and in CI console output — [Epic: Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)
- **Hutch Games (mobile racing, Ben Hallett, 12 Jul 2021)**: moved from a multi-step spreadsheet→export→database pipeline to direct Google Sheets API import, putting "all of our validation checks" in the import processor rather than scattered across spreadsheet conditional formatting, export tools and DB load. Catches schema mismatches, unexpected values and type mismatches. Key benefit: "the person that encounters the validation error is also much more likely to be the person that made the mistake in the spreadsheet in the first place." Also added data-hash versioning for rollback — [Hutch: For the love of spreadsheets](https://www.hutch.io/blog/tech/tech-blog-game-changer/)
- **Vendor/indie guidance on JSON content**: content files edited by humans "will eventually contain mistakes like a misspelled field, missing value, or reference to a non-existent entity"; validate on load against a schema (required fields, types, ranges, known enums) and report exact file/field rather than failing "deep in gameplay" — [bugnet.io: JSON content parse errors](https://bugnet.io/blog/how-to-fix-json-content-parse-error-crashing-on-bad-data); [bugnet.io: mod JSON with no validation](https://bugnet.io/blog/how-to-fix-data-driven-mod-json-with-no-validation-crashing-the-game) (vendor blog; secondary)

### Inferences
- Validation checks that matter most for a JSON-driven economy sim (SOLO-FIT, cheap, very high value): (a) parse errors with file name; (b) required fields present and right type; (c) numeric ranges (no negative durations/prices, no zero-length timers that cause divide-by-zero or infinite production in offline catch-up); (d) **cross-references** — every resource id used in a recipe exists, every recipe referenced by a building exists, every icon file named after a resource id exists; (e) unknown/misspelled keys flagged (typo "duraton" silently ignored is the classic data bug); (f) duplicate ids.
- Run the same validator in three places, mirroring Unreal: at game start in debug builds (fail loudly), in the headless test run (fail the run), and optionally as a quick standalone command before committing. Because the project's `GameData` autoload already centralizes loading, that is the natural single "import processor" Hutch describes.
- Release-build policy for bad data should differ: in development, stop or show a red error; in a shipped build, skip/neutralize the bad entry and log it, never brick the player's save.
- For the future MMO backend, the same validator can run server-side so client and server agree on content — one validator, many call sites.

### Gaps
- No primary studio source found on validating JSON *specifically* with JSON Schema in a shipped game; JSON-Schema advice above comes from vendor/indie blogs.
- No primary source fetched on large studios' spreadsheet linting (e.g. live-ops economy tuning validation at Supercell/King); unknown.

## 5. Automated safety nets: unit tests, invariants, monkey/random play, soak, replays, smoke tests/BVTs

### Takeaway
Automated testing of gameplay, once considered impractical, is now well documented at Rare (Sea of Thieves), Riot (League of Legends) and Wube (Factorio), and even small/mid studios (Croteam) used bots to replace daily manual playthroughs. The highest value-per-hour items for a small team are: tests for game rules (especially a test written for every bug before fixing it), a fast smoke/"build verification" run on every change, and deterministic replays/seeds so failures reproduce.

### Cited Findings
- **Factorio (Wube)**: started automated testing around 2014, positioned "something between unit testing and integration testing" — [FFF #60 "Tests all around"](https://factorio.com/blog/post/fff-60)
- **Factorio, FFF #366 "The only way to go fast is to go well!"**: QA ensures "any discovered bug is first covered by a test before it gets actually fixed"; coverage measured with OpenCppCoverage to highlight untested branches, aiming to "continuously raise the bar"; GUI tested via a mode where "the testing environment is created with GUI (even when tests are run without graphics)"; instead of heavy mocking they use "a simple test dependency system" so when debugging a test "you know that all of its dependencies are already working correctly"; author (kovarex) describes adopting TDD as "constant fast switching between extending the tests and making them pass continuously" — [FFF #366](https://factorio.com/blog/post/fff-366)
- **Factorio determinism checks ("heavy mode")**: the game CRCs the whole map every tick and saves the map each tick; a replay recomputes the CRC per tick and throws a desynchronization error on mismatch — used to find non-determinism (e.g. an electricity/accumulator desync bug found with heavy mode + replay in 0.17.60) — [Factorio wiki: Desync](https://wiki.factorio.com/Desync); [FFF #47 "CRC fun"](https://factorio.com/blog/post/fff-47); [Factorio forum bug report](https://forums.factorio.com/viewtopic.php?p=447616) (details from search snippets)
- **Sea of Thieves (Rare)**: built with automated gameplay testing "from day one"; Rare built an internal framework so team members could create tests easily — [GDC news, 2019](https://gdconf.com/news/sea-thieves-devs-share-automated-testing-tips-gdc-2019). GDC 2019 talk "Automated Testing of Gameplay Features in Sea of Thieves" (Robert Masella) notes gameplay automated testing "had traditionally not been embraced by the industry, due to the perceived time required and difficulty in creating reliable tests" and covers test types and appropriate coverage — [GDC Vault](https://gdcvault.com/play/1026366/Automated-Testing-of-Gameplay-Features). The project reportedly has "hundreds of thousands" of automated tests mixing unit, integration and actor tests — [Unreal Fest Europe 2019: Automated Testing at Scale in Sea of Thieves](https://www.unrealengine.com/events/unreal-fest-europe-2019/automated-testing-at-scale-in-sea-of-thieves) (figure from search snippet)
- **Riot, League of Legends (Jim Merrill, 26 Feb 2016)**: ~100,000 test cases run daily; ~5,500 per build in ~18 minutes; CI results within ~1 hour of check-in; organized as test sets incl. "BVSBlocker" smoke tests and "BVSCore" functional tests; new tests must sit in "BVSStaging" and prove stable for at least a week before promotion (staging failures only notify, to avoid noise from flaky tests); BVS caught ~50% of critical/blocker bugs; defects reported 1–2 hours after submission; bugs found by automation were resolved **8× faster** than average; "Automation frees up our quality analysts to focus on more creative testing" — [Riot: Automated Testing for League of Legends](https://www.riotgames.com/en/news/automated-testing-league-legends)
- **Croteam, The Talos Principle**: realized gameplay needed testing daily because small design changes could break puzzles but "couldn't afford the manpower"; built a bot using navigation/behaviour markers to solve every puzzle and report unsolvable ones; with rendering skipped (time-lapse), the full game took the bot ~20 minutes vs 4–5 hours (per-puzzle-run figure as reported) for a human; the bot logged the equivalent of 80,000 human playtime hours testing the Deluxe Edition and Road to Gehenna — [PlayStation Blog, 25 Sep 2015](https://blog.playstation.com/archive/2015/09/25/how-croteam-built-a-bot-to-beat-its-ps4-puzzler-the-talos-principle/feed)
- **Random-input ("monkey") testing with seeds**: Android's UI/Application Exerciser Monkey "generates pseudo-random streams of user events such as clicks, touches, or gestures"; stops and reports crashes, unhandled exceptions and ANRs ("application not responding"); "If you re-run the Monkey with the same seed value, it will generate the same sequence of events" (`-s <seed>`); `--throttle` slows it; typical run `adb shell monkey -p your.package.name -v 500` — [Android Developers: Monkey](https://developer.android.com/studio/test/other-testing-tools/monkey)
- **Asserts and tests reinforce each other**: Llopis notes good test frameworks treat assert failures like test failures and custom handlers can even test that an assert fires — [Llopis: Asserting Oneself](https://gamesfromwithin.com/asserting-oneself/)

### Inferences
- Value-per-hour ranking for a solo dev on a deterministic economy sim (inference from the above):
  1. **Rule tests for pure simulation code** (production timers, offline catch-up math, selling, save migration) — SOLO-FIT, cheapest, and the project already has `tests/test_simulation.gd`. Factorio's "bug gets a test before the fix" habit is the single most transferable rule.
  2. **Invariant checks** run after every simulated step in tests (and optionally in debug builds): money never NaN, stock never negative, never above capacity, `finishes_at >= started_at`, offline catch-up with clock moved backwards yields zero progress. SOLO-FIT.
  3. **Seeded random-play ("monkey") simulation**: a headless script that performs thousands of random legal actions (build, start job, sell, save/load, jump clock forwards/backwards) with a printed seed, checking invariants after each; a failing seed is a reproducible bug. SOLO-FIT, especially good for idle/business sims where the state space is large but rules are pure math. Android's Monkey is a free device-level complement for UI crashes.
  4. **Save round-trip and migration tests**: load every old save-format fixture, migrate, re-save, compare. SOLO-FIT, vital given the project's versioned saves and future MMO migration.
  5. **Smoke test / build verification**: the headless test run must pass before each commit (Riot's "BVSBlocker" idea at solo scale). SOLO-FIT if it runs in seconds.
  6. **Soak tests**: simulate months of offline/idle time in one call to catch overflow/precision drift; cheap for a sim because catch-up is one calculation.
  7. BIG-TEAM: large CI farms, staging lanes for flaky tests, coverage tooling, bot playthroughs with navigation markers, daily 100k-test runs.
- Determinism (same inputs + seed ⇒ same state) is what makes replays and monkey tests useful; it's also a prerequisite for the planned MMO (server-authoritative simulation, client prediction). Factorio's per-tick checksum is the gold-standard version; a solo dev can approximate by hashing the save dictionary after a seeded run and comparing across runs.
- Flaky tests are worse than no tests because they teach you to ignore red; Riot's one-week staging rule is the big-team cure, the solo cure is "no wall-clock time or real randomness in tests — inject the clock and seed" (consistent with the project's single `TimeService.now()` rule).

### Gaps
- Sea of Thieves test counts and test-type breakdown come from talk abstracts/search snippets; the talk itself (video/slides) was not reviewed.
- No primary source fetched on soak testing practices at specific studios.
- No hard data found comparing value-per-hour of different test types for small teams; the ranking above is inference.

## 6. Error codes vs exceptions, null-object fallbacks, defensive programming vs trusting internal data

### Takeaway
Most C++ game codebases historically ban or disable exceptions (cost, binary size, invisible control flow, hard to retrofit), handling failures with return values, asserts and fallbacks instead. The general principle that survives across languages: validate hard at trust boundaries (files, saves, network, player input), then trust internal data and guard it with asserts rather than defensive checks everywhere.

### Cited Findings
- **Google C++ Style Guide**: "We do not use C++ exceptions." Reasons: exception safety requires RAII and different coding practices, making control flow harder to read; adding a `throw` means examining "all of its transitive callers"; exceptions add data to every binary (compile time, address space); existing exception-unsafe code makes retrofitting "slow and error-prone"; error codes and assertions are the alternative — [Google C++ Style Guide: Exceptions](https://google.github.io/styleguide/cppguide.html#Exceptions)
- **Game-dev practitioner view (forum, not authoritative)**: enabling exceptions makes code larger and adds unwinding tables even if nothing is thrown, hurting instruction cache; "many studios" ban exceptions outright and almost all C++ game middleware avoids them — [GameDev.net: Performance with using exceptions in C++ game programming](https://gamedev.net/forums/topic/689321-performance-with-using-exceptions-in-c-game-programming/) (forum discussion; treat as practitioner opinion)
- **Null Object fallback**: `NullAudio` "basically does nothing, but it allows code that receives the object to safely continue on"; useful while dependent systems aren't built yet; downside: harder to notice an *unintentionally* missing service — [Nystrom: Service Locator](https://gameprogrammingpatterns.com/service-locator.html)
- **Programming errors vs user/content errors** need different handling: asserts are for programmer mistakes only; content-creator and player mistakes must be handled — [Llopis: Asserting Oneself](https://gamesfromwithin.com/asserting-oneself/)
- **Every path must report a result**: Unreal validators must call `AssetPasses` or `AssetFails` on each execution path — a structural guard against silent "no result" outcomes — [Epic: Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)

### Inferences
- For a language without (or not using) exceptions, the transferable patterns are: functions that can fail return an explicit result (ok/error + message) that the caller must look at; impossible states are asserts; recoverable *external* problems (missing file, corrupt save, bad JSON entry) get a clear log + safe fallback.
- A null-object/fallback should be **loud in development, quiet in release**: e.g. an unknown resource id returns a placeholder "missing" item *and* logs an error once; this keeps play-testing going without hiding the bug (addresses Nystrom's "harder to debug" drawback).
- SOLO-FIT trust-boundary map for this project: untrusted = `data/*.json` (validate at load), `user://` saves (validate + migrate, never crash; keep a backup), system clock (clamp backwards jumps — already a project rule), player input; trusted after validation = internal sim state (guard with asserts/invariants). Later, for the MMO: the server must treat every client message as untrusted, while the shared simulation rules stay pure and tested.
- Over-defensive code (checking for null everywhere "just in case") turns bugs into silent wrong behaviour; checking once at the boundary and asserting inside is the standard alternative.

### Gaps
- No primary source fetched confirming specific engines' exception settings (e.g. Unreal compiling with exceptions disabled by default, EASTL's no-exceptions design); widely believed but unverified here.

## 7. Common mistakes and anti-patterns

### Takeaway
The recurring anti-patterns all reduce visibility: asserts with side effects that vanish in release, error spam that buries the real error, silent fallbacks/swallowed errors, flaky tests that teach people to ignore failures, and validation scattered so far from the author that mistakes are found late by someone else.

### Cited Findings
- **Side effects in asserts**: stripped checks are not evaluated, so any side effect disappears in shipping; Unreal says asserts "must not have any side effects" and provides `verify` for expressions whose side effects must always run — [Epic: Asserts](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)
- **Spam / flooding**: ensure reports once per session specifically "to avoid flooding the crash reporter"; Unreal reserves Verbose/VeryVerbose levels for high-volume detail kept off by default — [Epic: Asserts](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine); [Epic: Logging](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)
- **Silent fallbacks hide bugs**: a null service "may be harder to debug an *unintentionally* missing service" — [Nystrom: Service Locator](https://gameprogrammingpatterns.com/service-locator.html)
- **Flaky tests**: Riot quarantines new tests in staging for a week and only notifies on staging failures, to prevent confusion — [Riot](https://www.riotgames.com/en/news/automated-testing-league-legends)
- **Validation far from the author**: Hutch found scattered checks (spreadsheet formatting, export tool, DB load) slowed fixes; centralizing means the person who sees the error is likely the one who made it — [Hutch](https://www.hutch.io/blog/tech/tech-blog-game-changer/)
- **Errors crashing "deep in gameplay" instead of at load** when data isn't validated — [bugnet.io](https://bugnet.io/blog/how-to-fix-json-content-parse-error-crashing-on-bad-data) (vendor blog)
- **Asserts that only reach a log on device** ("Assertion errors silent in development build") — [Unity Discussions](https://discussions.unity.com/t/assertion-errors-silent-in-development-build/944051) (title only)
- **Lazy design compounds**: Factorio's kovarex links duplicated, poorly designed code to poor productivity ("lazy long-term design leads to poor productivity") and argues "The only way to go fast is to go well!" — [FFF #366](https://factorio.com/blog/post/fff-366)

### Inferences
- Additional anti-patterns commonly warned against (inference; no single primary source fetched): empty catch-all handlers / ignoring returned error values; using "Error" severity for normal events so real errors drown; logging inside per-frame loops; vague messages ("something went wrong") with no ids/values; fixing a bug without adding a test, so it returns; tests that depend on the real clock, real randomness, or the real save file (the project memory already notes a script touching the real `user://save.json`).
- SOLO + AI-assistance specific risk: AI-generated code often adds broad "if x == null: return" guards that silently swallow problems. A house rule like "every early-return guard must log (once) why" and "use asserts for things that should be impossible" keeps errors visible.
