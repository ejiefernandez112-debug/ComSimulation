# Post-release error and crash reporting in games (detect, collect, act): state as of Oct 2026

Context for the report writer: these notes feed a plan for a solo developer with no prior coding experience, building a single-player business/idle sim in Godot 4.7 (GDScript), local JSON saves, offline production, Android first + PC, MMO backend (Firebase or Nakama) years later. "SOLO-FIT" marks things that suit that situation; "OVERKILL" marks things whose cost only pays off for bigger teams or online games. Godot is covered only as "does this service support Godot, and how" (another researcher covers Godot APIs). Research date: 2026-10-03. Prices are as shown on vendor pages fetched on that date unless marked otherwise; vendor pages change often, so re-check before buying.

Source-quality note: primary sources are vendor docs/pricing pages (Sentry, Firebase, Backtrace, BugSplat, BugSnag, Raygun, GlitchTip, GameAnalytics, Heroic Labs), Google Play / Android Developers / Apple / Steamworks docs, Godot docs, Factorio's own dev blog, and a law-firm summary of the COPPA amendments. bugnet.io (a Godot-focused crash-reporting vendor) publishes many unsigned SEO-style blog posts; they are cited only as "practice as described by a vendor" and flagged each time.

## 1. Crash/error reporting services: what they capture, what they cost, which work with Godot

### Takeaway
For a Godot game in 2026, **Sentry is the only major crash/error service with an official Godot SDK**: it catches GDScript errors with stack traces as well as engine crashes on Windows/Linux/macOS/Android/iOS/Web, and has a free 1-user tier of 5,000 errors/month. Firebase Crashlytics is free with no quota but only reaches Godot through a community plugin (Android/iOS only, manual logging). Backtrace, BugSplat, BugSnag and Raygun target Unity/Unreal/native apps and don't advertise Godot. Steam's built-in crash reporting is legacy and 32-bit-Windows-only. Google Play's Android vitals works with zero code (section 2).

### Cited Findings
**Sentry (official Godot SDK)**
- **Pricing (fetched Oct 2026)**: Developer plan $0, 1 user, 5,000 error events/month, 5 GB logs, 50 session replays, 1 GB attachments, 30-day retention, email alerts. Team $26/mo billed annually (unlimited users, 50,000 errors, up to 90-day retention, integrations/API). Business $80/mo billed annually. Enterprise custom — [Sentry pricing](https://sentry.io/pricing/)
- **Official SDK** `getsentry/sentry-godot`: MIT licence, C++ GDExtension built on Sentry's native/Android/Cocoa SDKs. SDK 1.x/2.x require **Godot 4.5+** (0.x supported 4.3+). Platforms: Windows, Linux, macOS, Android (arm64, arm32, x86_64, x86), iOS, Web (since 1.4.0), C#/.NET (since 2.0.0). Console forks "coming in 2026" — [GitHub: getsentry/sentry-godot](https://github.com/getsentry/sentry-godot)
- **Why 4.5+ is needed**: Sentry's 1.0-alpha post (23 Jul 2025) says Godot 4.5 added built-in script stack traces in exported games and a new logger interface with accurate line numbers, which made full GDScript stack traces possible. 1.0 added native crash reporting on Windows/macOS/Linux, Android export support, optional capture of local/member variables, file attachments, and no-op builds for unsupported platforms. The post mentions no formal partnership with the Godot Foundation — [Sentry blog: Godot SDK 1.0 alpha](https://blog.sentry.io/introducing-sentrys-godot-sdk-1-0-alpha-with-support-for-godot-4-5-beta). Sentry calls itself "the first application monitoring tool to directly support Godot" — [sentry.io/for/godot](https://sentry.io/for/godot)
- **18 Nov 2025 update**: added structured logs (every `print()` and engine message captured and searchable next to issues) and player user feedback. Platforms confirmed: Windows, Linux, macOS, iOS, Android. PlayStation/Switch crash reporting is available through Sentry without the SDK. No named Godot games or studios mentioned — [Sentry blog: Logs and User Feedback in the Godot SDK](https://blog.sentry.io/introducing-logs-user-feedback-godot-sdk)
- **What it captures automatically**: Godot runtime errors including script and shader errors; GDScript stack traces with optional local/member variables; surrounding script source; GPU/CPU/platform info; breadcrumbs and structured logs; scene-tree attachments; screenshots (experimental); log-file attachments; sessions and crash-free metrics (Release Health). Install: download the release (2.3.0 at fetch time), copy `addons/sentry` into the project, set the DSN in Project Settings — [Sentry docs: Godot](https://docs.sentry.io/platforms/godot/)

**Firebase Crashlytics**
- **Free** ("No-cost") on both Spark and Blaze plans; Google Analytics for Firebase is also no-cost — [Firebase pricing](https://firebase.google.com/pricing)
- **Report contents (Android)**: automatic fatal crashes and ANRs; custom keys; custom log messages; an anonymous user identifier; non-fatal exceptions (logged on the device and sent with the next fatal report or on app restart); breadcrumb logs from Google Analytics events; GWP-ASan native memory-error reports; opt-in reporting by turning off automatic collection — [Firebase: Customize Crashlytics reports (Android)](https://firebase.google.com/docs/crashlytics/customize-crash-reports?platform=android). Numeric limits (from an older, Fabric-era third-party guide; not confirmed in current Google docs): at most 64 key/value pairs of up to 1 KB each; only the 8 most recent logged exceptions per session are kept — [CodePath: Crash Reporting with Crashlytics](https://guides.codepath.com/android/Crash-Reporting-with-Crashlytics)
- **In Godot, Crashlytics comes only from a community plugin**: "GodotX Firebase" (github.com/godot-x/firebase, MIT) packages native Firebase modules as Android .aar / iOS .xcframework through an EditorExportPlugin. The current README says it requires "Godot 4.7-stable", iOS 13+ and Android SDK 24+, plus the Android Gradle build template and `google-services.json`. GDScript functions: `initialize()`, `set_user_id()`, `set_custom_value_string/int/bool/float()`, `log_message()`. The README doesn't say GDScript errors are captured automatically, and there's no desktop support — [godot-x/firebase README](https://raw.githubusercontent.com/godot-x/firebase/main/README.md). (An older search snippet described it as built against Godot 4.5-stable and Firebase Android SDK 33.5.1 — [godot-x/firebase](https://github.com/godot-x/firebase).)

**Other crash services (none advertise Godot)**
- **Backtrace (owned by Sauce Labs)**: Developer plan free for individuals, 25,000 errors/month, 1-month retention, 10 GB storage, covering mobile/PC/console/server. The Standard plan is priced per user per year: $600 (mobile), $900 (mobile+PC), $1,200 (adds consoles/servers), up to 1M errors/month, 3-month retention, 100 GB. Professional is custom (unlimited errors, on-prem option). The pricing page names Unity and Unreal, not Godot — [Backtrace pricing](https://backtrace.io/pricing)
- **BugSplat**: Free $0 forever, 3 users, 100 GB, 15,000 crashes/month, 1-month retention. Team $37/mo (annual), 25,000 crashes, 3-month retention. Business $208/mo (annual), 50,000 crashes, 6-month retention, PII obfuscation. Enterprise custom, includes consoles. Lists Unreal, Unity and consoles, not Godot — [BugSplat pricing](https://www.bugsplat.com/pricing/)
- **BugSnag (SmartBear; still branded BugSnag)**: Free $0, 1 user, 7,500 events + 1M spans/month, 7-day retention. Select/Preferred are tiered (50K–3M events), 60-day retention. 14-day trial. No game engines mentioned — [BugSnag pricing](https://www.bugsnag.com/pricing/)
- **Raygun**: no free plan (14-day trial). Basic $40/mo annual ($60 monthly) per 100,000 errors; Team $80/mo per 200,000; Business $400/mo per 1M; 180-day retention; $0.001 per extra error. No game engines mentioned — [Raygun pricing](https://raygun.com/pricing)
- **GlitchTip** (open-source, self-hostable error tracker; hosted in the US or EU/Germany): Free hosted tier 1,000 events/month; Small $15/mo for 100K; Medium $50/mo for 500K; Large $250/mo for 3M — [GlitchTip pricing](https://glitchtip.com/pricing). (GlitchTip markets itself as accepting Sentry SDKs, but the pricing page didn't say so and compatibility with the Godot SDK wasn't verified; see Gaps.)
- **Self-hosted Sentry** needs at minimum "4 CPU Cores, 16 GB RAM + 16 GB swap, 20 GB Free Disk Space" (32 GB RAM recommended), "with no guarantees or dedicated support" — [Sentry developer docs: Self-hosted](https://develop.sentry.dev/self-hosted/). OVERKILL for a solo dev.
- **Unity Cloud Diagnostics is deprecated**: in Unity 6.2+ the built-in "Diagnostics" service replaces it (adds ANR reporting and session breadcrumbs). Cloud Diagnostics Advanced (Backtrace-powered) stopped onboarding and fully shut down in Q3 2025, and Unity points advanced users to Backtrace — [Unity Discussions: Legacy Cloud Diagnostics deprecation](https://discussions.unity.com/t/deprecation-of-legacy-cloud-diagnostics-transition-to-new-diagnostics/1677370); [Unity Discussions: CDA deprecation](https://discussions.unity.com/t/deprecation-announcement-cloud-diagnostics-advanced-cda/1488742/1); [Unity docs: Migrate to Diagnostics](https://docs.unity.com/en-us/cloud-diagnostics/migration). Unity-only, so irrelevant to Godot.
- **Steam Error Reporting is legacy**: "Steam error reporting is nearing its End-Of-Lifetime and only limited support is available"; "The error reporting API currently only supports 32-bit applications on Windows". It uses `SteamAPI_SetMiniDumpComment` + `SteamAPI_WriteMiniDump` from a Win32 exception translator; "Steam will automatically upload mini dumps of any exception after 10 similar exceptions are thrown"; reports appear on the Error Reports page of the Steamworks partner site — [Steamworks: Steam Error Reporting](https://partner.steamgames.com/doc/features/error_reporting)

**Analytics vendors with error events**
- **GameAnalytics**: free tier with no MAU cap and no credit card, and it includes a "Health: Errors" feature. AnalyticsIQ Pro $49/mo; PipelineIQ Pro from $499/mo — [GameAnalytics pricing](https://gameanalytics.com/pricing). Its Godot SDK has Error events with severity `debug`/`info`/`warning`/`error`/`critical`, and "unhandled exceptions & crashes will be automatically sent over as error events" with filename/function/line when available — [GameAnalytics docs: Godot event tracking](https://docs.gameanalytics.com/event-tracking-and-integrations/sdks-and-collection-api/game-engine-sdks/godot/event-tracking)
- **Bugnet (bugnet.io)**: a small vendor that markets automatic crash/error capture "from real Godot players" plus bug reports. Its pricing page returned 404 at fetch time — [bugnet.io blog: crash reporting in Godot](https://bugnet.io/blog/best-practices-for-crash-reporting-in-godot)

### Inferences
- **SOLO-FIT: Sentry Developer (free)** is the most natural fit. It's the only service that understands GDScript errors (which never crash the process, so crash-only tools never see them), it covers both Android and PC with one SDK, and 5,000 errors/month is plenty for a small single-player game *if* repeated errors are throttled (the SDK does this by default, section 3). Limits to know: 1 user, 30-day retention, and once the quota runs out, events are dropped until the month resets.
- **Google Play Android vitals** (section 2) is the zero-effort baseline for Android and should be watched whatever else is chosen. It sees engine crashes and ANRs but not GDScript errors.
- Crashlytics is free with no quota, but in Godot it means a community plugin, a Gradle build, Android/iOS only, and no automatic GDScript error capture. It fits better later if the MMO backend ends up on Firebase. Using Crashlytics *and* Sentry together means duplicate crash handlers, so pick one.
- Backtrace, BugSplat, Raygun, BugSnag, Luciq and self-hosted Sentry or GlitchTip: OVERKILL or poorly matched (no Godot SDK) for this project.
- Steam's built-in reporter can't be used for a 64-bit Godot 4 export. *(Inference: Godot 4's standard desktop exports are 64-bit; the 32-bit restriction is quoted above.)*

### Gaps
- The Sentry Developer plan's overage behaviour wasn't confirmed (whether pay-as-you-go can be added on the free plan, or only on paid plans).
- Couldn't confirm whether GodotX Firebase includes the Crashlytics NDK module. Without it, native engine crashes on Android might not be captured.
- GlitchTip's compatibility with the Sentry Godot SDK wasn't verified.
- Bugnet pricing wasn't available.
- No independent survey of which crash tools Godot indies actually use. Search results were dominated by vendor content, and no r/godot thread with usable data was retrieved.

## 2. Google Play Console Android vitals: thresholds and store visibility

### Takeaway
Google Play collects crash and ANR data from opted-in Android users with no SDK at all. If an app's **user-perceived crash rate goes above 1.09%** of daily users (or 8% on any one phone model), or its **user-perceived ANR rate above 0.47%** (8% per model), judged on roughly the last 28 days of data, Play may reduce its visibility and show a warning on its store listing. New memory and code-optimization vitals may start affecting visibility from February 2027.

### Cited Findings
- **Core vitals that affect Play visibility**: user-perceived crash rate, user-perceived ANR rate, excessive partial wake locks (all apps), excessive battery usage (watch faces), memory usage, and bitmap memory usage — [Android Developers: Android vitals](https://developer.android.com/topic/performance/vitals)
- **Bad-behaviour thresholds**: user-perceived crash rate 1.09% overall / 8% per phone model; user-perceived ANR rate 0.47% overall / 8% per phone model; excessive partial wake locks 5%. "If your app or game exceeds a bad behavior threshold, Play may reduce the visibility of your title. Play may also show users a warning on your store listing." Apps over the memory, bitmap-memory or code-optimization thresholds "may see store visibility impact starting from February 2027" — [Android Developers: Android vitals](https://developer.android.com/topic/performance/vitals)
- **Definitions**: user-perceived crash rate = "The percentage of your daily users who experienced at least one user-perceived crash", meaning crashes while in the foreground or running a foreground service. Only "input dispatching timed out" ANRs count as user-perceived. A daily user is "a user using the app in a single day on a single device". Play "generally consider[s] the last 28 days of data" — [Play Console Help: Android vitals metrics](https://support.google.com/googleplay/android-developer/answer/9844486)
- **No code needed**: "Data is collected from users who have opted in to automatically share usage and diagnostics data from a subset of Android devices and OS versions." Data covers 90 days in Play Console and 3 years via the Play Developer Reporting API, updated daily. You can filter by app version (the "Artifact" dimension) and compare against a chosen peer group of apps. The Crashes and ANRs page groups crashes into clusters, and "the higher the number of affected users, the more that cluster contributes to your crash rate" — [Play Console Help: Monitor technical quality with Android vitals](https://support.google.com/googleplay/android-developer/answer/7385505?hl=en)
- **Symbols**: native crashes without function names need a native debug symbols file uploaded to Play Console. "Null pointer exceptions are the largest cause of app crashes on Google Play" — [Android Developers: Crashes](https://developer.android.com/topic/performance/vitals/crash)

### Inferences
- SOLO-FIT: Android vitals costs nothing and needs no code, so it's the minimum post-release monitor for an Android-first game. Its limits: it only sees crashes and ANRs (not GDScript errors or wrong numbers), only from opted-in users, a day or more late, and it's useless for PC.
- An ANR here means the game's main thread froze long enough that Android's input dispatch timed out. For an idle game, a long offline catch-up calculation or a large JSON save/load on the main thread at startup is the obvious risk. (Inference; the catch-up-as-one-calculation rule in this project's CLAUDE.md helps here.)
- The per-phone-model 8% threshold means one bad GPU driver or one low-RAM device family can trigger a warning even when the overall rate is fine. That's why a crash tool that reports device and GPU info (Sentry does) matters for Android.

### Gaps
- Didn't find exactly how big a phone model's user base must be before the per-model threshold applies.
- The new memory/code-optimization thresholds (per RAM tier) weren't extracted in detail.

## 3. Non-fatal errors, grouping, rate limiting, error-free sessions

### Takeaway
Modern tools treat "handled" errors as first-class events. They group duplicates into issues by fingerprint (mainly the stack trace), throttle repeats on the device so one error inside a per-frame loop can't burn the monthly quota, and track **crash-free and error-free session/user rates per release**. Sentry's Godot SDK ships with sensible throttles (at most 5 events per frame, identical errors at most once per second, 20 events per 10 s).

### Cited Findings
- **Sentry session states**: Healthy (ended normally, no errors); Errored (ended normally but had handled errors); Crashed (hard crash); Unhandled (an unhandled error that didn't end the process, tracked separately since v25.9.0); Abnormal (SDK can't tell whether the session ended gracefully, e.g. the battery died). Crash-free sessions = % of sessions not ending in a crash; crash-free users = % of distinct users with no crash. Release adoption over 24 h: Adopted (≥10% of sessions), Low Adoption (<10%), Replaced — [Sentry docs: Release Health](https://docs.sentry.io/product/releases/health/)
- **Sentry Godot SDK error routing and throttling (defaults)**: `godot_logger.event_mask` = 13 (native, script and shader errors become events); `breadcrumb_mask` = all (errors, warnings, script, shader and messages become breadcrumbs); `log_mask` = none. `godot_logger.limits`: `events_per_frame` 5; `repeated_error_window_ms` 1000 (an identical error at most once per second); `throttle_events` 20 per `throttle_window_ms` 10000 (sliding window). `sample_rate` 1.0. A `before_send` callback can edit an event or return `null` to drop it — [Sentry docs: Godot options](https://docs.sentry.io/platforms/godot/configuration/options/)
- **Sentry grouping**: events with the same fingerprint form one issue. Default order: custom fingerprint → stack trace (in-app frames: module, filename, code context) → exception type/value → message, plus ML-based similarity grouping. You can merge/unmerge issues, add fingerprint or stack-trace rules, or set fingerprints in code; changes only affect new events — [Sentry docs: Event grouping](https://docs.sentry.io/concepts/data-management/event-grouping/)
- **Sentry quotas**: Spike Protection is a per-project dynamic rate limit that drops events above a threshold computed from your quota and 7-day usage patterns. Once the monthly quota is used up, further events are discarded unless a pay-as-you-go budget exists. Rate limits can also be set per DSN key — [Sentry docs: Spike protection](https://docs.sentry.io/pricing/quotas/spike-protection/)
- **Crashlytics** non-fatals are stored on the device and sent with the next crash or on restart — [Firebase: Customize Crashlytics reports](https://firebase.google.com/docs/crashlytics/customize-crash-reports?platform=android). Crash-free users = 1 − crashed users / all users; crash-free sessions = 1 − crashed sessions / all sessions. Newer SDKs (Android 18.6.0+, Apple 10.8.0+, Unity 11.7.0+) no longer need Google Analytics for these numbers — [Firebase: Crash-free metrics](https://firebase.google.com/docs/crashlytics/crash-free-metrics). A "regressed" issue is a closed issue that comes back — [Firebase: Crashlytics troubleshooting](https://firebase.google.com/docs/crashlytics/troubleshooting)
- **GameAnalytics error events** carry five severity levels (debug, info, warning, error, critical) — [GameAnalytics docs: Godot event tracking](https://docs.gameanalytics.com/event-tracking-and-integrations/sdks-and-collection-api/game-engine-sdks/godot/event-tracking)
- **Crash-free targets for indies** (vendor blog with unsourced numbers; a rule of thumb only): ">99% crash-free sessions is a reasonable launch target"; "most indie games start around 95–97% after launch"; 99.5%+ means a well-polished game — [bugnet.io: good crash-free rate](https://bugnet.io/blog/whats-a-good-crash-free-rate-for-an-indie-game). Google's own hard line for Android is the 1.09% user-perceived crash rate (section 2).
- Industry precedent for "report once": Unreal's `ensure` reports a non-fatal to the crash reporter once per session to avoid flooding (covered in the sibling notes file `dev_time_practices.md`).

### Inferences
- SOLO-FIT: keep the SDK's default throttles. For a game with per-frame production ticks, one bad recipe in JSON could otherwise fire an error 60 times a second on every device.
- Useful severity split for this project: **crash** (process died) → fix first; **error** (GDScript error, failed save write, failed JSON load, broken invariant like negative stock or money going NaN) → send as a non-fatal event with release + save version; **warning** → breadcrumb only (attached to the next real event, not sent alone).
- "Errored sessions" (Sentry) is the right health number for a GDScript game. Most GDScript failures leave the game running in a broken state instead of crashing, so crash-free rate alone would look misleadingly good.

### Gaps
- Didn't verify how Sentry fingerprints GDScript errors specifically (by script path + line, or by message). Errors whose message embeds changing values could split into many issues.
- No primary studio source found on rate-limiting policy for non-fatals in shipped indie games.

## 4. Release tagging and symbolication

### Takeaway
Every report must carry the exact build version, so you can tell which release introduced a bug, confirm a hotfix worked (crash-free rate per release), and match native stack traces to the right debug symbols. GDScript stack traces arrive readable without any upload. Native (engine) crash traces need debug symbols: Godot now publishes them for its official Android export templates, but Sentry says desktop templates still need a custom build.

### Cited Findings
- **Sentry attaches every event to a `release`**. The Godot SDK defaults it to `"{app_name}@{app_version}"` from project settings ("must be unique across all projects in your organization"), and `environment` is auto-detected (release export vs editor vs headless) — [Sentry docs: Godot options](https://docs.sentry.io/platforms/godot/configuration/options/). Release Health (crash-free %, adoption) is computed per release — [Sentry docs: Release Health](https://docs.sentry.io/product/releases/health/)
- **GDScript needs no symbols; native crashes do**: "The official Godot Engine builds only provide templates without debug information files". Readable native traces need custom export templates built with `scons target=template_release production=yes debug_symbols=yes separate_debug_symbols=yes`, uploaded with `sentry-cli debug-files upload --include-sources --org … --project … bin`. Android also needs the Swappy library, a Gradle build, and arm32+arm64 templates — [Sentry docs: Godot readable stack traces](https://docs.sentry.io/platforms/godot/configuration/stack-traces)
- **Newer and partly contradicting, from Godot's own docs**: native debug symbols for official **Android** export templates can be downloaded from each stable GitHub release (e.g. `Godot_native_debug_symbols.4.5.1.stable.template_release.android.zip`). They can be uploaded to Play Console (Test and release → Latest releases and bundles → bundle → Downloads → Assets → "Native debug symbols") or used locally with `ndk-stack -sym …/arm64-v8a/ -dump crash.txt`. Without them, Play Console and Crashlytics show unreadable native traces — [Godot docs: Resolving crashes on Android](https://docs.godotengine.org/en/latest/tutorials/platform/android/resolving_crashes_on_android.html)
- **Play Console filters vitals by app version** (the "Artifact" dimension) — [Play Console Help: Android vitals](https://support.google.com/googleplay/android-developer/answer/7385505?hl=en)

### Inferences
- SOLO-FIT: tie three numbers together and attach all of them to every report: the game version (Godot `application/config/version`, which Sentry uses automatically), the Android `versionCode` (must go up on every Play release, see section 8), and the **save-file `save_version`** (this project already keeps one). Many idle-game bugs only show up when an old save meets new code.
- For a GDScript-only game, most actionable reports will be GDScript errors, which are readable without symbols. Native symbols only matter for engine-level crashes (GPU drivers, out-of-memory). The cheap win is uploading Godot's official Android symbols to Play Console. Custom desktop templates are OVERKILL at first.

### Gaps
- Didn't confirm from which Godot version official Android symbols are published (4.5.1 is the documented example), or whether desktop symbols are planned.
- Didn't verify whether Sentry can use Godot's official Android symbol zip directly.

## 5. In-game player bug reporting

### Takeaway
Studios pair **automatic** crash upload (players almost never report crashes themselves) with a **player-initiated** report path that attaches logs, the save and system info. Factorio found a dozen crashes in two days that nobody had reported on its forum. Klei and Paradox run public bug trackers/forums and ask for log + save + crash folder. For Godot, Sentry's SDK includes a ready-made feedback form that attaches a screenshot and can link to the crash it follows.

### Cited Findings
- **Factorio (Wube) automatic crash-log upload, FFF #231, 23 Feb 2018**: uploads "basic system information (CPU, GPU and free memory), game display settings, operation log, crash stack trace" and sometimes minidumps, never save games. It's **opt-out** (can be turned off in options) because with opt-in "very few people will actually check the options and alter the default behaviour". The server parses stack traces and groups identical crash logs to rank them by frequency. Within 2 days of 0.16.24 they found "about 12 crashes that were found by our reporting tool, none of which were reported on the forum" — [Factorio FFF #231](https://www.factorio.com/blog/post/fff-231)
- **Factorio FFF #285, 8 Mar 2019**: "over 12,000 crash reports automatically sent in for 0.17"; 372 active reports on the bug forum; the worst issues came from side effects of later fixes, not the initial release — [Factorio FFF #285](https://www.factorio.com/blog/post/fff-285)
- **Klei (Oxygen Not Included)**: bugs go to the public Klei Bug Tracker. Klei asks for `player.log` (send it before relaunching, because a relaunch overwrites it), the latest save (auto_save folder), and crash folders containing a log, a text crash file and a DMP — [Klei support: ONI crashing at the Klei logo](https://support.klei.com/hc/en-us/articles/360036947812-Oxygen-Not-Included-is-crashing-at-or-just-after-the-Klei-Logo). Players on the tracker report the in-game crash reporter sometimes fails to upload, possibly with saves over 12 MB or behind firewalls/VPNs. This comes from a search summary of [Klei bug tracker: crash report fails](https://kleiforums.com/klei-bug-tracker/oni_so/crash-report-fails-r42673/); the page returned 403, so it's unverified.
- **Paradox**: per-game bug-report forums with a template. For crashes, devs ask players to zip and attach the crash folder (e.g. Stellaris: Documents/Paradox Interactive/Stellaris/crashes) plus `error.log` and the save game, per dev replies indexed on devtrackers.gg — [devtrackers.gg: Stellaris crash thread](https://devtrackers.gg/stellaris/p/4d1eb998-stellaris-crushed) (secondary aggregator)
- **Sentry Godot SDK user feedback (SDK 1.1.0+)**: `SentrySDK.capture_feedback(feedback)` with `message` (required) and optional `name`, `contact_email` and `associated_event_id` (links the feedback to a crash/error event). The SDK attaches a screenshot automatically and ships ready-made scenes: `addons/sentry/user_feedback/user_feedback_gui.tscn` (drop it under a CanvasLayer and call `show()`) and `user_feedback_form.tscn`, with a `minimum_words` setting. It captures on the next frame so the screenshot shows the game, not the form — [Sentry docs: Godot user feedback](https://docs.sentry.io/platforms/godot/user-feedback/)
- **Instabug is now Luciq**: announced at droidcon Berlin, Sept 2025, as "Agentic Mobile Observability" — [BusinessWire, 24 Sep 2025](https://www.businesswire.com/news/home/20250924435921/en/Instabug-Becomes-Luciq.ai-Pioneers-New-Category). Capterra (2026) lists one contact-sales Enterprise plan with a free trial and no free version — [Capterra: Luciq pricing](https://www.capterra.com/p/166279/Instabug/pricing/). OVERKILL.
- **BugSplat** customer Disruptive Games (Unreal): "Just push a button instead of hunting down logs" (vendor customer story) — [BugSplat: Disruptive Games](https://www.bugsplat.com/customers/disruptive)
- **Discord intake** (vendor blog): use a dedicated Discord Forum channel with a pinned bug-report template as the *intake*, route reports into a real tracker, and combine it with an in-game reporter that captures device metadata automatically — [bugnet.io: bug reports from Discord](https://bugnet.io/blog/best-practices-for-collecting-bug-reports-from-discord-communities) (vendor blog); BetaHub sells a Discord-forum-to-tracker integration — [BetaHub: Discord forum integration](https://betahub.io/resources/setup-discord-forum-integration-betahub/)

### Inferences
- SOLO-FIT: a "Report a bug" button in settings that sends **message + screenshot + recent log + game/save version + device info**, plus optionally the JSON save. Small text saves make attaching them practical, unlike Klei's 12 MB saves. Sentry's feedback scene covers most of this with almost no code. Save attachments need care: Sentry's free tier allows 1 GB of attachments per month (section 1), and a save may contain a player-chosen company or town name (section 7).
- An "email us with attachments" fallback, or a Discord Forum channel, is fine early on, but players won't find log files on Android (the user:// folder is private to the app), so an in-game button matters more on mobile than on PC.
- Factorio's lesson applies directly: forum/Discord reports massively undercount crashes, so automatic reporting is what finds them.

### Gaps
- No primary source found for RimWorld's or Don't Starve's reporting tools, or for what exactly Klei's in-game crash reporter uploads (the Klei forums blocked fetching).
- No first-hand source on how mobile idle/tycoon games (e.g. Kairosoft) handle in-game bug reports.

## 6. Telemetry and analytics that catch bugs indirectly

### Takeaway
Many economy-sim bugs don't throw errors; they produce *wrong numbers*. Studios catch them with analytics: source/sink tracking of currencies, progression funnels showing where players drop off, and custom "design" events for impossible states. GameAnalytics (free, Godot SDK, built-in source/sink economy events) and Aptabase (privacy-first, Godot SDK, no consent banner claimed) fit an indie Godot game; Firebase Analytics is free but in Godot only reachable via the community plugin.

### Cited Findings
- **GameAnalytics resource events model an economy as sources and sinks**, e.g. `addResourceEvent("source", "gold", 100, "quest", "kill_dragon_quest", {})` and `("sink", "gold", 100, "shop", "fire_sword", {})`. Dashboards show Flow (balance), Sink and Source. Progression events (start/fail/complete) give funnels, design events (1–5 colon-separated segments) carry custom signals, and error events have severities — [GameAnalytics docs: Godot event tracking](https://docs.gameanalytics.com/event-tracking-and-integrations/sdks-and-collection-api/game-engine-sdks/godot/event-tracking). Free tier with no MAU cap — [GameAnalytics pricing](https://gameanalytics.com/pricing)
- **Aptabase**: open-source, "privacy-first" analytics with a Godot SDK (Godot 4.2+). It claims no personal data, cookies, device identifiers or fingerprinting, and so "no consent banner". Free up to 20,000 events/month; paid from $10/mo (200K events) to $450/mo (50M). Nothing is tracked automatically; each event gets OS, app version and locale added — [Aptabase for Godot](https://aptabase.com/for-godot) (vendor's own claims; the "no consent needed" claim is the vendor's legal position, not verified)
- **Google Analytics for Firebase limits (app streams)**: 500 distinctly named events per app; event names ≤40 characters; 25 parameters per event; parameter values ≤100 characters; 25 user properties; 100,000 events per user per day — [Firebase Help: Collection limits](https://support.google.com/firebase/answer/9237506). No-cost — [Firebase pricing](https://firebase.google.com/pricing)
- **Unity Analytics** (comparison point for consent norms): since SDK 5.0.0 it collects nothing until `StartDataCollection()` is called. "If consent is given call `AnalyticsService.Instance.StartDataCollection()`… If consent is not given, don't call this method" — [Unity docs: Opt-in compliance](https://docs.unity.com/en-us/analytics/privacy-and-consent/manage-data-privacy/sdk-compliance-opt-in)
- **Mega Crit (Slay the Spire)**: GDC 2019 talk "'Slay the Spire': Metrics Driven Design and Balance" (Anthony Giovannetti). A metric-driven focus from early development through a year of weekly Early Access updates, combined with community feedback — [Game Developer, 29 Jan 2019](https://www.gamedeveloper.com/design/learn-i-slay-the-spire-i-s-metrics-driven-approach-to-game-balancing-at-gdc-2019); [GDC Vault](https://www.gdcvault.com/browse/gdc-19/play/1025731). (Talk details beyond the abstract not verified.)

### Inferences
- SOLO-FIT, and cheaper than any analytics service: **on-device sanity checks that report through the error tool**. For example, money or stock negative, NaN or above a sane cap; offline catch-up producing more than the theoretical maximum for the elapsed time; a clock moving backwards; a save that fails validation on load. Each sends a non-fatal error with release + save_version. This catches "impossible values" without a full analytics pipeline. (Inference; ties in with the invariant tests already in this repo.)
- A simple progression funnel (finished tutorial → built Wheat Farm → Flour Mill → Bakery → first sale) shows where players get stuck. A sudden drop after an update is often a bug, not a design problem.
- For a single-player offline game, full analytics is optional at launch. Crash/error reporting gives more value per unit of privacy risk. Analytics becomes more important with the MMO phase (economy exploits, server-side validation).

### Gaps
- No primary studio postmortem found showing a bug caught specifically by economy telemetry in an idle/tycoon game.
- PostHog's free tier and error-tracking allowances couldn't be read (pricing page didn't render).

## 7. Privacy and law

### Takeaway
Automatic crash reporting is "data collection" for both Google Play's Data safety form and Apple's privacy label, and has to be declared, including data sent by third-party SDKs. Under GDPR the legal basis is genuinely contested: a German law-firm guide recommends opt-in consent for telemetry, while widespread practice (Factorio, many indies) is opt-out with legitimate interest. The safe low-effort pattern is: send no personal data, scrub file paths and IDs, disclose it in a privacy policy, and give an in-game toggle. Asking on first launch is safest for EU players. Child-directed apps carry extra US (COPPA) and Play Families duties.

### Cited Findings
- **Google Play Data safety**: "Crash logs" = "Crash log data from your app. For example, the number of times your app has crashed, stack traces, or other information directly related to a crash." "Diagnostics" = "Information about the performance of your app. For example battery life, loading time, latency, framerate, or any technical diagnostics." "Collect" means "transmitting data from your app off a user's device", including via "libraries and/or SDKs used in your app, irrespective of whether data is transmitted to you or a third-party server". Exemptions: ephemeral processing and end-to-end-encrypted data. The form also asks about encryption in transit and deletion requests (or automatic deletion/anonymization within 90 days) — [Play Console Help: Data safety section](https://support.google.com/googleplay/android-developer/answer/10787469)
- **What Firebase says to declare**: Crashlytics collects crash logs ("Stack traces", "Relevant application state"), a device ID ("Crashlytics installation UUID") and diagnostics ("Relevant device metadata"), automatically, for "Track, prioritize, and fix app stability issues". Remote Config collects app ID/package name plus diagnostics (country, language, time zone, OS/platform/SDK version) — [Firebase: Play data disclosure](https://firebase.google.com/docs/android/play-data-disclosure)
- **Apple App Privacy label**: the Diagnostics category covers Crash Data ("Such as crash logs"), Performance Data ("Such as launch time, hang rate, or energy use") and Other Diagnostic Data. Data is "linked to you" unless de-identified before collection. Disclosure is optional only if ALL of these hold: not used for tracking, not used for ads, collected infrequently and optionally, and provided by the user through a form each time. Apple's example is "optional feedback forms or customer service requests" — [Apple: App privacy details](https://developer.apple.com/app-store/app-privacy-details/)
- **GDPR basis is contested**: activeMind.legal (V. Paschou, 7 Mar 2023) argues telemetry is personal data, advises against legitimate interest ("The processing of telemetry data is outside what users would objectively reasonably expect"), and recommends opt-in consent before first start that's as easy to revoke as to give — [activeMind.legal: Telemetry data](https://www.activemind.legal/guides/telemetry-data/). In contrast, Factorio ships crash upload as opt-out — [Factorio FFF #231](https://www.factorio.com/blog/post/fff-231). A vendor blog says most indies anonymize IDs, rely on legitimate interest, disclose it and offer an opt-out (vendor, not legal advice) — [bugnet.io: crash reporting & GDPR](https://bugnet.io/blog/crash-reporting-gdpr-indie-games). Published game privacy policies show both bases in use, e.g. nDreams cites legitimate interest for crash reporting — [nDreams: Oh My Galaxy privacy policy](https://ndreams.com/oh-my-galaxy-privacy-policy)
- **ePrivacy Art. 5(3)** requires consent for storing or reading information on a user's device unless it's strictly necessary, and the CJEU has held that the GDPR consent standard applies. This comes from search summaries; the primary texts weren't fetched (see Gaps).
- **CNIL (France) mobile-app recommendations** (Sept 2024; page dated 13 May 2025): apps need consent for data "not necessary for their operation"; the recommendations set out roles for publishers, developers, SDK providers, OS makers and stores — [CNIL: Mobile applications](https://cnil.fr/en/node/166141). Secondary sources say CNIL's spring-2025 checks target SDK behaviour, and that an SDK must not start consent-requiring processing before consent — [SecurePrivacy (FR)](https://secureprivacy.ai/fr/blog/conformite-rgpd-des-applications-mobiles-cnil-sdk-et-consentement-2026)
- **Unity's default is opt-in**: Unity Analytics collects nothing until the developer calls `StartDataCollection()` after consent (or where no consent law applies and the player hasn't opted out) — [Unity docs: Opt-in compliance](https://docs.unity.com/en-us/analytics/privacy-and-consent/manage-data-privacy/sdk-compliance-opt-in)
- **Scrubbing tools**: Sentry Godot SDK `send_default_pii` defaults to false — [Sentry docs: Godot options](https://docs.sentry.io/platforms/godot/configuration/options/). Sentry's server-side scrubbing removes credit-card-like values and fields named like password/secret/api_key/auth/credentials/token by default. "Prevent Storing of IP Addresses" is a separate setting, and geolocation is still derived from the IP even when that's on. Advanced rules (regex) can scrub custom patterns. The docs don't say usernames in file paths are scrubbed by default — [Sentry docs: Server-side scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/). On Windows, Godot's `user://` is `%APPDATA%\Godot\app_userdata\[project_name]` (macOS `~/Library/Application Support/…`, Linux `~/.local/share/godot/…`) — [Godot docs: Data paths](https://docs.godotengine.org/en/stable/tutorials/io/data_paths.html)
- **COPPA (US, under-13s)**: the amended Rule took effect 23 June 2025, with full compliance by **22 April 2026**. The "support for internal operations" exception (collecting only a persistent identifier, solely for internal operations) is unchanged, but the notice must now list those operations and the safeguards against behavioural advertising. A written data-retention policy is required and indefinite retention is banned — [Latham & Watkins: FTC publishes updates to COPPA Rule](https://www.lw.com/en/insights/ftc-publishes-updates-to-coppa-rule)
- **Google Play Families policy** (target audience includes children): don't transmit AAID, SIM serial, build serial, BSSID, MAC, SSID, IMEI or IMSI from children or unknown-age users, and don't request the AD_ID permission when targeting API 33+. The self-certified SDK rule covers *ads* SDKs, but every SDK must be "approved for use in child-directed services" — [Play Console Help: Families policy](https://support.google.com/googleplay/android-developer/answer/9893335)

### Inferences
- **Paths are the main PII leak for a desktop Godot game.** `%APPDATA%` resolves to `C:\Users\<Windows username>\…`, so any error message, log line or stack frame that includes an absolute path can carry the player's real name. Use `before_send` (on the device) or a Sentry advanced scrubbing rule to replace `C:\Users\<name>` and `/home/<name>` with a placeholder. *(Inference from Windows path conventions plus the docs above.)*
- Also keep out: player-typed names (company/town names in saves), email addresses (only if the player types them into a feedback form, which falls under Apple's optional-form case), and IPs (turn on "Prevent Storing of IP Addresses").
- SOLO-FIT, low legal risk: (1) no ads SDKs and no ad IDs; (2) crash/error reporting with PII off, path scrubbing, IP storage off; (3) a privacy policy listing crash logs + diagnostics, the vendor (Sentry, US/EU region) and retention (30 days on Sentry free); (4) an in-game "Send crash reports" toggle; (5) for EU players, ideally a one-time first-launch prompt, because the legitimate-interest route is disputed. Declare "Crash logs" and "Diagnostics" (collected, not shared, encrypted in transit, purpose: app functionality/analytics) on Play's Data safety form. *(Inference; not legal advice.)*
- A business/idle sim with a general audience is normally not "directed to children", but cute art plus Play's target-age settings can pull it into Families policy. Avoid persistent identifiers beyond the SDK's installation ID if the audience might include under-13s.

### Gaps
- Didn't find an EDPB or regulator statement specifically on crash reporting (as opposed to analytics) and whether it can be "strictly necessary" under ePrivacy Art. 5(3). EDPB Guidelines 2/2023 on Art. 5(3) weren't fetched.
- Whether Sentry's Godot SDK stores anything on the device before consent (and so falls under ePrivacy) wasn't checked. Delaying SDK initialization until consent is the cautious pattern but wasn't verified as supported in Godot.
- Didn't verify the details of the Sentry DPA or EU data region on the free plan.

## 8. Workflow after a report arrives: triage, hotfix, staged rollouts, beta channels

### Takeaway
Rank issues by **number of affected users** in the current release (Play's clusters and Sentry/Factorio-style grouping do this automatically), reproduce with the attached log and save, fix, and ship through a channel that limits damage. On Play that means internal/closed testing tracks plus **staged rollouts**, which can be halted but never rolled back, so the fix is always a new, higher version code. Play review can take up to a week. On Steam, beta branches let you test patches and re-publish an older build. Play's mandatory 12-tester/14-day closed test for new personal accounts doubles as an early-warning system.

### Cited Findings
- **Prioritise by affected users**: on Play's Crashes and ANRs page, "the higher the number of affected users, the more that cluster contributes to your crash rate" — [Play Console Help: Android vitals](https://support.google.com/googleplay/android-developer/answer/7385505?hl=en). Factorio groups identical crash logs to rank fixes by frequency — [Factorio FFF #231](https://www.factorio.com/blog/post/fff-231)
- **Staged rollouts**: updates only (not a first launch). You choose a percentage and it "won't increase automatically". Users are picked at random per release, and halting then resuming affects "the same set of users". Halting doesn't roll back: "Users who already received the app version in your staged rollout version will remain on that version", so you must ship a new release with a higher version code. Country-targeted rollouts are possible, but countries can't be removed once started — [Play Console Help: Staged rollouts](https://support.google.com/googleplay/android-developer/answer/6346149)
- **Play review time**: processing "can take a few hours or up to seven days (or longer in exceptional cases)". Managed publishing lets you control when an approved update goes live, and Google suggests planning at least a week's buffer — [Play Console Help: Managed publishing / review times (search summary)](https://support.google.com/googleplay/android-developer/answer/9859654)
- **Testing tracks**: internal testing up to 100 testers, available "within minutes"; closed testing up to 200 lists × 2,000 users; open testing is visible on Play — [Play Console Help: Set up testing](https://support.google.com/googleplay/android-developer/answer/9845334)
- **New personal accounts (created after 13 Nov 2023)**: "At least 12 testers must be opted in to your closed test when you apply for production access, and they must have been opted in continuously for the preceding 14 days". The application asks about the test, the app and production readiness — [Play Console Help: App testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465)
- **Pre-launch report**: when you upload an AAB/APK (subject to lab capacity), Google installs the app on real devices and crawls it "for several minutes", reporting stability, compatibility, performance and accessibility issues with stack traces and screenshots — [Play Console Help: Pre-launch report](https://support.google.com/googleplay/android-developer/answer/9842757)
- **In-app updates**: "Immediate updates are fullscreen UX flows that require the user to update and restart the app… best for cases where an update is critical to the core functionality of your app". Update priority 0–5 is set via the Play Developer API. Android 5.0+ and Play installs only. Official support covers Kotlin/Java, native, Unity and Unreal, with no Godot listing — [Android Developers: In-app updates](https://developer.android.com/guide/playcore/in-app-updates)
- **Steam beta branches**: created on the App Admin Builds page, optionally password-protected (which also hides the branch name). Players opt in via Properties → Game Versions & Betas. A build can't be set live on the default branch automatically: "You must do that manually in App Admin" — [Steamworks: Branches](https://partner.steamgames.com/doc/store/application/branches)
- **Studio evidence (vendor case studies)**: Team17 used Backtrace so developers could see what happened in a crash without waiting for QA repro steps; THQ Nordic reportedly halved time to identify/resolve — [Unity: Backtrace](https://unity.com/products/backtrace) (from a search summary of the vendor page). Disruptive Games watches BugSplat during playtests — [BugSplat](https://www.bugsplat.com/customers/disruptive). Factorio: the worst post-release bugs came from side effects of fixes — [FFF #285](https://www.factorio.com/blog/post/fff-285)

### Inferences
- SOLO-FIT release loop: build → internal track (yourself, minutes) → closed track (the 12+ required testers; watch Sentry and the pre-launch report) → production at a small staged percentage (e.g. 5–10%) → watch crash-free/errored-session rates for that release for a day or two → increase. If it's bad, halt and ship a higher-versionCode fix. (The percentages are a common pattern; Google doesn't prescribe them.)
- Factorio's lesson argues for treating every hotfix as a release in its own right (tests + staged rollout), not a rushed push.
- Because a Play fix can take days to clear review and halting can't undo an update, the **kill switch (section 9) and defensive save loading** are the only same-day mitigations on Android.
- On Steam, the equivalent is a public "beta" branch for early adopters and re-setting the previous build live as a rollback.

### Gaps
- Didn't fetch an indie postmortem with concrete triage numbers (time to fix, rollout percentages).
- Couldn't verify whether Play's "halt" + "resume a previous release" flow allows serving an older version to *new* installs. The docs say you must ship a higher version code.

## 9. Remote config, kill switches, feature flags

### Takeaway
A kill switch is a server-side flag the game reads at startup to turn a broken feature off without an app update. That matters most on Android, where review and rollout delays mean a fixed build can take days. Options range from a static JSON file on any web host (free, SOLO-FIT), to Firebase Remote Config (free up to 100,000 fetches/day; new pay-as-you-go pricing from 1 Sept 2026), to Heroic Labs Satori (feature flags with a Godot client, pairs with Nakama). For a single-player offline game it must fail safe: no network means use cached or default values.

### Cited Findings
- **Firebase Remote Config pricing (2026)**: "Starting September 1st 2026, Remote Config will offer a flexible pricing structure… a no-cost plan and a scalable pay-as-you-go tier based on your daily usage". Free up to 100,000 fetch requests/day/project (Spark and Blaze); Blaze beyond that costs $0.06 per 10K requests (100,001–10M/day) and $0.01 per 10K above 10M/day. Existing Spark projects start billing 1 Dec 2026; 30-day grace before throttling — [Firebase: Remote Config pricing](https://firebase.google.com/docs/remote-config/pricing). Google describes its purpose as changing "behavior and appearance of your app without publishing an app update" — [Firebase: Play data disclosure](https://firebase.google.com/docs/android/play-data-disclosure)
- **Godot access to Remote Config**: the GodotX Firebase listing names Core, Analytics, Crashlytics and Messaging modules, with no Remote Config module in the descriptions found — [godot-x/firebase](https://github.com/godot-x/firebase) (not exhaustively verified against the latest README)
- **Heroic Labs Satori** (LiveOps companion to Nakama): each remotely configurable value is a feature flag, "a named setting that your game reads from the server instead of from its own code". No limit or billing difference by number of flags. The Satori Godot client ships inside the Nakama Godot SDK, but Nakama isn't required; Godot 4 — [Heroic Labs: Satori remote configuration](https://heroiclabs.com/docs/satori/concepts/remote-configuration/); [Satori Godot client](https://heroiclabs.com/docs/satori/client-libraries/godot/). Pricing not public in the sources found.
- **Kill-switch pattern** (vendor blog): a server-controlled boolean read at startup, at its simplest a JSON config file on a CDN. Flip it, then post an in-game/Discord notice, fix, test, ship, re-enable and write a postmortem — [bugnet.io: How to write a killswitch](https://bugnet.io/blog/how-to-write-a-killswitch-for-critical-bugs) (vendor blog, unsigned)
- **Play In-app updates "immediate" flow** works as a "forced update" for critical fixes — [Android Developers: In-app updates](https://developer.android.com/guide/playcore/in-app-updates)

### Inferences
- SOLO-FIT: a tiny versioned JSON file (e.g. on GitHub Pages or any static host) such as `{ "min_version": 12, "disabled_features": ["retailer_sell"], "message": "…" }`, fetched with a short timeout at startup, cached, and ignored if unreachable. It covers three needs at almost no cost: turn off a broken feature, show a notice, and tell very old versions to update. It fits this project's data-driven design (tuning already lives in JSON), but a remote file must never be required to play offline. Remotely overriding *tuning numbers* also needs validation (bounds checks), or a typo in the remote file becomes a live bug for everyone. *(Inference.)*
- Firebase Remote Config or Satori make sense when the MMO backend arrives (Firebase or Nakama respectively). Adopting either now is OVERKILL for an offline single-player game.
- A kill switch must not break offline-progress timestamps or saves. Disabling a building type should pause it, not delete it from the save. *(Inference.)*

### Gaps
- No primary first-party studio source (GDC talk or studio blog) on kill-switch use in mobile games was retrieved. The pattern description here relies on a vendor blog plus Google's description of Remote Config.
- Satori pricing and free-tier terms weren't found.
- No official Godot plugin for Play In-app updates was verified (community plugins likely exist, but weren't checked).
