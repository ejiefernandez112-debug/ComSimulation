# Make every error loud, then safe

Game developers handle errors with one rule: during development, make every problem impossible to miss, and after release, make every problem survivable for the player while still reaching the developer. During development that means sorting problems into "this should be impossible" (stop and complain loudly), "this is wrong but survivable" (complain once and keep going), and "bad input from a file or player" (check it at the door and report exactly what was wrong). It also means automated checks that run on every change: tests for game rules, validation of data files, and random-play bots. After release, studios degrade gracefully instead of crashing, protect saves with several layers of backups and version upgrades, give players one tap to hand over diagnostics, and collect crashes automatically, because players almost never report them. Factorio found about 12 crashes in two days that nobody had mentioned on its forum ([Factorio](https://factorio.com/blog/post/fff-231)). For this project the most important finding is Godot-specific. A **release export of a GDScript game skips most runtime error checks and silently carries on with a `null` value**, so a hidden bug can quietly write bad data into the save. The project's existing safety net (error counting in headless tests, the project/data check, the random-play invariant test, safe save writing, the debug-only dev panel) is already ahead of most solo projects. The highest-value next steps are cheap: refuse to write a broken save, keep backups spaced out in time, show errors on screen in debug builds, and adopt a few house rules for AI-written code. Crash-reporting services can wait until outside testers arrive.

## Studios sort errors into three kinds before writing a single check

The oldest piece of advice in game programming is to separate *programmer mistakes* from *user mistakes*. Noel Llopis put it as: an assert is "a message from the programmers to the programmers and nobody else" ([Llopis](https://gamesfromwithin.com/asserting-oneself/)). An **assert** is a one-line check in the code that says "this must be true here, and if it isn't, something is broken". It documents an assumption and fires the moment that assumption breaks. Llopis calls them "exploding comments". Mistakes in data files, saves or player input are a different category. They must be handled with a clear message, never with a crash.

Unreal Engine, the most thoroughly documented engine, turns this into three tools that map onto three severities ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)). `check` halts the program when internal state is corrupt. It is **stripped out of the shipped game and its expression is not even evaluated there**, which is why Epic warns that checks "must not have any side effects". A side effect is any real work, like spending money or saving a file, hidden inside the check. A separate `verify` exists for exactly that case: it always runs. `ensure` is the middle tier. It reports a non-fatal problem and keeps running, and it reports **only once per session "to avoid flooding the crash reporter"**. This "report once" idea solves the classic playtest problem where one broken thing inside a loop that runs 60 times a second prints thousands of identical lines and buries everything else. Unity follows the same pattern: its asserts exist only in development builds ([Unity](https://docs.unity3d.com/ScriptReference/Assertions.Assert.html)).

The second principle is *where* to check. Most C++ game code avoids exceptions, a language feature that throws an error up through the program until something catches it. The Google C++ Style Guide states flatly "We do not use C++ exceptions" because they make control flow hard to follow ([Google](https://google.github.io/styleguide/cppguide.html#Exceptions)). Without them, the consistent pattern is: **check hard at the trust boundaries, then trust internal data and guard it with asserts**. Trust boundaries are the places where outside data enters: data files, save files, the system clock, player input, and later the network. Robert Nystrom's *Game Programming Patterns* shows the trade-off of the alternative, a quiet "null object" fallback that does nothing when something is missing. It "lets us keep running the game", but makes an *unintentionally* missing piece much harder to notice ([Nystrom](https://gameprogrammingpatterns.com/service-locator.html)). The resolution most practitioners reach is to make fallbacks **loud in development and quiet in release**.

This matters more than usual for a solo developer working with an AI assistant. The research notes flag a specific risk: AI-generated code tends to add broad guards like `if x == null: return`, which quietly skip the work and turn a bug into silent wrong behaviour. Two house rules counter it cheaply. Every early-return guard logs once *why* it gave up, naming which building or resource was involved. And anything that "should be impossible" becomes an assert, never a silent skip. Asserts also work as executable documentation. When a later AI edit breaks an assumption that nobody wrote down elsewhere, the assert fires.

## An error nobody sees is an error that ships

Mature engines log through named categories (one per system: economy, saves, data) with an ordered ladder of severities. Unreal's ladder runs from Fatal ("prints … then crashes") through Error and Warning down to Verbose detail that stays off by default ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)). Three details from Unreal are worth copying. Logs always go to a **file** as well as the screen, so they survive a crash. Verbosity can be raised per system while the game runs. And in Unreal's command-line tools, **an Error-level log line marks the whole run as failed**, which turns the log into an automatic test signal. The project's headless tests already do exactly this with their Logger-based error counter.

Crash-reporting vendors add the idea of **breadcrumbs**: a small in-memory "ring buffer" (a list that keeps only the most recent entries, typically the last 20 to 50 events, overwriting the oldest) that gets attached to a crash report so the developer can see what led up to it ([bugnet.io, vendor blog](https://bugnet.io/blog/how-to-add-breadcrumbs-to-your-games-crash-reports)). The useful thing to log is *state changes* (job started, offline catch-up computed 7,200 seconds, save migrated from v4 to v5), not values every frame. A good error message names what (which building or resource id), where (which file and field), expected versus actual, and what the game did about it ("skipped this recipe").

Logs only help if someone reads them, so engines also put problems **on screen**. Unreal's `AddOnScreenDebugMessage` shows colored temporary overlays, and its in-game console can change log levels while the game runs ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)). The common failure mode is captured in a Unity forum thread titled "Assertion errors silent in development build" ([Unity Discussions](https://discussions.unity.com/t/assertion-errors-silent-in-development-build/944051)): on a phone, errors that only go to a log are effectively invisible. The cheap indie pattern is a small red counter in a screen corner of debug builds ("3 errors, 12 warnings") that opens the recent-error list when tapped, plus a brief pop-up the first time each distinct error happens. For an idle sim, the companion is a debug panel that can skip time, force an offline catch-up of N hours and reload data. Time-based bugs are otherwise painfully slow to reproduce. The project's `scenes/debug/dev_panel` gated by `OS.is_debug_build()` already follows this rule.

## Data checks and automated play catch bugs before a human plays

### Validate data files where they enter, at the field that's wrong

Studios treat data files as code that needs checking. Unreal's Data Validation system runs custom rules automatically when an asset is saved, on demand, and **headless in CI** ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)). "Headless" means without a window, from a command line. CI ("continuous integration") means a server that runs the checks automatically on every change. Each validator must explicitly pass or fail on every path, so no check can end silently. Mobile studio Hutch moved "all of our validation checks" into one import step and found the payoff was human: "the person that encounters the validation error is also much more likely to be the person that made the mistake" ([Hutch](https://www.hutch.io/blog/tech/tech-blog-game-changer/)). For a JSON-driven economy, the checks that matter most are parse errors with the file name; required fields and types; numeric ranges (no zero-length timers that make offline catch-up divide by zero); **cross-references** (every resource a recipe uses exists); duplicate ids; and unknown keys, because a misspelled key like `"duraton"` is silently ignored. The project's `tests/check_project.gd` already covers nearly all of these, including the unknown-key check. It currently reports unknown keys as non-failing NOTEs. Turning them into failures is a one-line decision.

### Test the rules, play randomly, and make every failure replayable

Automated gameplay testing was long considered impractical. Rare's Sea of Thieves talk notes it "had traditionally not been embraced by the industry" ([GDC Vault](https://gdcvault.com/play/1026366/Automated-Testing-of-Gameplay-Features)). It is now well documented. Riot runs about 100,000 League of Legends test cases daily, and **bugs found by automation were resolved 8× faster than average** ([Riot](https://www.riotgames.com/en/news/automated-testing-league-legends)). Croteam, unable to afford daily human playthroughs of The Talos Principle, built a bot that solved every puzzle in about 20 minutes and logged the equivalent of 80,000 human playtime hours ([PlayStation Blog](https://blog.playstation.com/archive/2015/09/25/how-croteam-built-a-bot-to-beat-its-ps4-puzzler-the-talos-principle/feed)). The single most transferable habit comes from Factorio: **"any discovered bug is first covered by a test before it gets actually fixed"** ([Factorio FFF #366](https://factorio.com/blog/post/fff-366)). That stops fixed bugs from coming back.

Random-input testing works best when every run is replayable. Android's Monkey tool fires pseudo-random taps at an app and reports crashes. "If you re-run the Monkey with the same seed value, it will generate the same sequence of events" ([Android Developers](https://developer.android.com/studio/test/other-testing-tools/monkey)). A **seed** is a starting number for the random generator, so the same seed always produces the same "random" game. Factorio takes this furthest: in a special mode it checksums the entire map every tick and replays to find the exact moment two runs diverge ([Factorio Wiki](https://wiki.factorio.com/Desync)). That property, the same inputs always giving the same result, is called **determinism**. It is also what a future server-authoritative MMO needs.

The project's `tests/test_invariants.gd` is a solo-scale version of all of this. An **invariant** is a rule that must always hold, such as "stock is never negative". The test plays hundreds of seeded random games with real data and clock jumps backwards. It checks invariants after every step, compares "time away" with "playing through it", round-trips saves, and prints the seed so a failure can be replayed. The one gap the notes surface is the old-save library. The test already loads every save in `tests/saves/` and has a `--make-save-sample` option, but that folder does not exist yet, so no real old-format save is being tested. Flaky tests, ones that sometimes fail for no real reason, are worse than none because they teach you to ignore red. Riot quarantines new tests for a week for exactly that reason. The solo cure is already a project rule: no real clock and no real randomness inside tests.

## Godot's release builds keep running silently, so design around it

### No try/catch, and release exports skip the checks

GDScript has no exceptions. A forum answer in May 2026 to "how do I catch errors?" was simply "You don't" ([Godot Forum](https://forum.godotengine.org/t/how-to-catch-errors-thrown-by-gdscript-objects/138519)). The idiom has three parts. Functions that can fail return an `Error` code or `null` that the caller checks. `push_error`/`push_warning` report problems. And `assert` handles programmer-only checks, which "is only executed in debug builds or when running the project from the editor" ([Godot docs](https://docs.godotengine.org/en/latest/classes/class_@gdscript.html)). The research team read the engine source and found the critical behaviour that ties the whole report together. In the editor and in debug builds, a script error (reading a missing dictionary key, calling a method on `null`) prints an error with a **backtrace** (the chain of function calls that led there), stops that function and returns a default value. In a **release export the checks are compiled out entirely**: the error-check macro "expands to nothing", the bad read yields `null`, and the next line runs with no message ([gdscript_vm.cpp](https://github.com/godotengine/godot/blob/master/modules/gdscript/gdscript_vm.cpp); [SConstruct](https://github.com/godotengine/godot/blob/master/SConstruct)). An experiment on the installed Godot 4.7.2 confirmed the editor behaviour. The release behaviour rests on source reading, because Windows Application Control blocked the unsigned export templates on this PC.

Three consequences follow. First, **"no errors in the release log" does not mean "no script bugs"**, so builds for outside testers should be *debug* exports. Second, save-writing code must validate what it writes with explicit checks, never relying on runtime errors or asserts that don't exist in release. Third, `push_error` and engine-side errors (a failed file open, a broken JSON parse) *are* reported in every build type ([error_macros.h](https://github.com/godotengine/godot/blob/master/core/error/error_macros.h)), so **explicit `push_error` calls at the key checkpoints are what make a release build observable at all**. The project's scripts currently contain only a handful of such calls.

### The Logger class is the foundation of everything else

Godot 4.5 added the `Logger` class and `OS.add_logger()`. Any code can now intercept every error and message the engine produces, along with a script backtrace, and the release notes explicitly envision "a tool for reporting bugs within your game" ([Godot 4.5](https://godotengine.org/releases/4.5/)). The API is unchanged through 4.7, so the project's existing `_ErrorCounter` is forward-compatible. Building on it has four non-obvious traps, which the team confirmed by experiment.

First, the message text arrives in different places. For `push_error` and script errors the text is in `code` with `rationale` empty, while engine errors like JSON failures put it in `rationale`. Godot's own tutorial comment "The error text is in `rationale`" is only sometimes true, so use whichever is non-empty. Second, for `push_error` the reported file and line point at Godot's C++ source; the actual script line is in the first backtrace frame. Third, the methods "will be called from threads other than the main thread, possibly at the same time" ([Logger docs](https://docs.godotengine.org/en/latest/classes/class_logger.html)). A **thread** is a separate line of work the engine runs in parallel. A Logger that stores errors in a list therefore needs a `Mutex` (a lock that lets only one thread touch the list at a time) and must hand data to the screen through the main thread. Fourth, you cannot call `print` or `push_error` from inside a Logger, because that would loop forever. In release builds backtraces are empty unless `debug/settings/gdscript/always_track_call_stacks` is turned on. It is off "for performance", and no official cost figure exists ([ProjectSettings](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html)).

### Android writes no log file by default

Godot writes `user://logs/godot.log` (five kept, rotating) **only on desktop by default**. On Android nothing is written to a file, and even if it were, `user://` is private app storage the player can't browse ([ProjectSettings](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html); [Data paths](https://docs.godotengine.org/en/latest/tutorials/io/data_paths.html)). Release builds also buffer plain `print` output until exit, so lines just before a crash can be lost. `push_error`, `push_warning` and `printerr` go to stderr, which is flushed every time ([Logging tutorial](https://docs.godotengine.org/en/latest/tutorials/scripting/logging.html)). The practical answer is the project's own small error log, written through a Logger, which behaves the same on PC and Android. For data files, switching from `JSON.parse_string()` to a `JSON` instance gives `get_error_line()` and `get_error_message()`, so the game can show *which line* of a data file is broken ([JSON docs](https://docs.godotengine.org/en/latest/classes/class_json.html)). Note also that JSON has only one number type and turns integers into floats.

### Let the compiler catch bugs before they run

Every GDScript warning is a project setting that can be set to Ignore, Warn or Error. Set to Error, a warning stops the script from compiling ([warning system](https://docs.godotengine.org/en/latest/tutorials/scripting/gdscript/warning_system.html)). The type-safety warnings (`untyped_declaration`, `unsafe_property_access`, `unsafe_method_access`, `unsafe_call_argument`) are **off by default**. With static typing (declaring that a variable holds, say, an `int`), "GDScript can detect more errors without even running the code" ([static typing](https://docs.godotengine.org/en/latest/tutorials/scripting/gdscript/static_typing.html)). Turning these on converts many would-be silent release failures into compile errors. The project's `check_project.gd` already compiles every script headlessly, and `--check-only` returns a failure exit code in 4.7 ([main.cpp](https://github.com/godotengine/godot/blob/4.7/main/main.cpp)), so those errors would be caught automatically. There is a one-off cleanup cost, because data read from JSON is untyped and needs explicit types. The gentle route is Warn first, then Error once each folder is clean.

### Existing tools are enough, apart from on-device debugging

The project's hand-rolled test harness (a headless script, a Logger error counter, an exit code) is essentially what the GUT and GdUnit4 frameworks do internally. Both support 4.7, but switching isn't needed ([GUT](https://github.com/bitwes/Gut); [GdUnit4](https://github.com/godot-gdunit-labs/gdUnit4)). For seeing errors from a real phone, Godot's one-click deploy installs a debug build over USB or Wi-Fi and streams its script errors into the editor's Errors tab ([one-click deploy](https://docs.godotengine.org/en/latest/tutorials/export/one-click_deploy.html)). That is the main development workflow for Android-only bugs. If a typed-command console is ever wanted, LimboConsole is maintained (v0.8.0, June 2026), while the popular Panku Console has had no release since July 2024 ([LimboConsole](https://github.com/limbonaut/limbo_console); [Panku](https://github.com/Ark2000/PankuConsole)). One last detail: `OS.is_debug_build()` stops the dev panel from *running* in release, but its files still ship unless an export filter excludes `scenes/debug/` ([OS docs](https://github.com/godotengine/godot/blob/4.7/doc/classes/OS.xml)).

## Players forgive a broken feature faster than a lost save

### Switch off the broken part, say so in one sentence, never block the exit

Shipped games rarely stop on a non-fatal error. They isolate the likely culprit, disable or reset it, and tell the player plainly. Factorio shows a "Disable all mods / Restart / Exit" dialog instead of crashing on a broken mod ([Factorio forums](https://forums.factorio.com/viewtopic.php?p=267919)). The Sims 4 turns mods off after every major patch and says so at the next launch ([EA](https://help.ea.com/en-us/help/the-sims/the-sims-4/mods-and-the-sims-4-game-updates)). Two cautionary tales sharpen the pattern. X-Plane's automatic "your last run crashed, reset settings?" prompt annoyed users so much that it moved behind a held Shift key ([X-Plane](https://developer.x-plane.com/2015/08/a-slightly-better-safe-mode/)). Cities: Skylines II's error pop-up offers Continue, Quit and a useful "Copy" button, but a broken mod can raise it again and again so the player never reaches the menu where the mod could be switched off ([Steam](https://steamcommunity.com/app/949230/discussions/0/4361249459071461316)). **An error dialog must group repeats and must never block the way out.** Destiny's word-based error codes (WEASEL, BANJO) show the value of a short, quotable identifier players can repeat to support ([PCGamesN](https://www.pcgamesn.com/destiny-2/error-codes)). The project already writes good plain-English save messages ("The save file is damaged.") but has no stable code like `SAVE-DAMAGED` to search for in reports.

### Several layers protect a save, and the project has the first two

Shipped games stack defences. The first is the **atomic write** (the save happens all-or-nothing): write a temporary file, then rename it over the old one, so a crash mid-write never leaves half a save. Factorio "renames the old one, saves new one and when that succeeds deletes the old one" ([Factorio forums](https://forums.factorio.com/viewtopic.php?p=419421)). The project does this, keeps one backup, and keeps unreadable files under a new name instead of overwriting them. The 2009 ext4 incident shows the gap in this layer. Apps that renamed without forcing the data to the physical disk first could end up with an **empty file after a power cut**, because the rename was recorded before the data ([LWN](https://lwn.net/Articles/322823/)). The research did not establish whether Godot's file close forces data to disk. Reading the temp file back and parsing it before the swap catches truncation either way, for almost no cost on a small JSON file.

The bigger gap is **backups spaced out in time**. The Sims 4 keeps five older versions per slot ([SimsCommunity](https://simscommunity.info/2015/02/13/sims-4-tutorial-restore-previous-saved-game/)). The open-source idle game Antimatter Dimensions keeps eight automatic slots refreshed at 1 minute, 5 minutes, 20 minutes and 1 hour, plus slots written **just before offline progress is applied** and a reserve slot ([AD source](https://github.com/IvarK/AntimatterDimensionsSourceCode/blob/master/src/core/storage/storage.js)). The project's single backup is replaced on every save: every 30 seconds, after actions, and on pause. So it is only seconds older than the main file. It protects against a torn write but **not against a logic bug that writes valid-looking but wrong data**, because within seconds both copies are bad. The same mechanism means "Start over" erases the old game within about 30 seconds, as a code comment admits. Real incidents show what goes wrong in practice. Cyberpunk 2077 corrupted saves that grew past 8 MB, and the patch could not repair saves already damaged ([TechSpot](https://www.techspot.com/news/88082-latest-cyberpunk-2077-patch-fixes-saved-game-corruption.html)). Early-access Windrose wrote up to about 108 GB per hour to disk through near-continuous autosaving and backups until it was patched to save every 10 minutes ([AllThings.How, secondary](https://allthings.how/windrose-high-ssd-usage-explained-and-fixed-patch-0-10-0-4/)).

### Refuse to save what is broken, and repair what loads

The best examples check *values*, not just structure. Antimatter Dimensions walks the entire save looking for **NaN** ("not a number", the result of something like dividing zero by zero) and rejects a save that contains any. After upgrading a save, it fills any missing field from defaults ([AD source](https://github.com/IvarK/AntimatterDimensionsSourceCode/blob/master/src/core/storage/storage.js)). Stardew Valley's SMAPI removes content that no longer exists and logs one specific line per repair: "Removed invalid building type … (Did you remove a custom building mod?)" ([SMAPI source](https://git.nea.moe/github/SMAPI.git/tree/src/SMAPI.Mods.ErrorHandler/Patches/SaveGamePatcher.cs)). The project's `_check_shape()` and `_drop_unknown()` already do the structural half, with player-visible notes. What's missing is the value half. `_is_number()` accepts NaN and infinity. Nothing checks for negative stock, duplicate building ids or timestamps far in the future. Resources inside a building's storage and recipes inside its queue are not checked against current data. Most importantly, **the same check doesn't run before saving**, which is what stops a logic bug from spreading into the main file and its backup. The research left one open question: how Godot's `JSON.stringify` writes NaN, and whether `JSON.parse` can read it back. A save-time guard closes that risk either way.

### Upgrade old saves step by step, and refuse newer ones politely

Long-lived games give every save one ever-increasing integer version. Minecraft introduced its "data version" because display versions like "1.14" can't be compared, and it offers a backup before upgrading an old world ([Minecraft Wiki](https://minecraft.wiki/w/Data_version)). Factorio records which upgrade steps (**migrations**) each save has had, so each runs exactly once ([Factorio API](https://lua-api.factorio.com/latest/auxiliary/migrations.html)). The project's `_migrate()` chain matches this model. It is missing two things. One is a permanent pre-migration copy, because the original is otherwise gone two saves after the upgrade. The other is a dedicated "newer version" path. Today a save from a newer version is renamed as unreadable and **a new game starts**. Factorio instead stops with "Map version … can't be loaded because it's higher than the game version". This case will grow with Android backup restores, device transfers and the eventual cloud sync.

### Distrust the clock gently

Single-player idle games mostly tolerate clock cheating or answer it with in-fiction consequences. Animal Crossing rots turnips after time travel rather than blocking it ([Nookipedia](https://nookipedia.com/wiki/Time_travel)). Hard enforcement appears where cheating affects other players. Unix timestamps ignore time zones, but AdVenture Capitalist players report daylight-saving changes alone glitched timers ([Steam](https://steamcommunity.com/app/346900/discussions/0/492378806376401622)), a warning for any future "daily" feature defined in local time. The project already clamps negative offline time to zero. The open decision is what happens to jobs whose finish time is now "in the future" after a backward clock jump. They freeze until real time catches up, which could be months if a phone's clock was wrong and then auto-corrected. Either accept the freeze as a natural penalty, or shift all stored timestamps back by the jump in one calculation. Either way, log it.

### On Android, the player can't reach their own save

Android 11 closed `Android/data/` even to file managers, and Stardew players who can no longer back up their saves have asked in vain for a choosable save location ([Stardew forums](https://forums.stardewvalley.net/threads/android-option-to-change-the-save-game-location.25172/latest)). Android Auto Backup is a safety net, not a backup system. It runs at most once every 24 hours, keeps only the latest copy, caps an app at 25 MB, restores only on reinstall, and "some devices may never back up" ([Android Developers](https://developer.android.com/identity/data/autobackup)). An in-game **Export/Import save** (via the share sheet or copyable text, as idle games commonly offer) is therefore the most practical safety net an offline Android game can give its players. It is also the only realistic way for a player to send a save to the developer. Factorio's habit of keeping the previous session's log next to the current one ([Factorio Wiki](https://wiki.factorio.com/Log_file)) avoids Klei's problem of telling players to grab the log *before relaunching* ([Klei](https://support.klei.com/hc/en-us/articles/360029555392)).

## After release, automatic reports find crashes players never mention

Players almost never report crashes. Factorio's opt-out crash upload found 12 crashes in two days that "none of which were reported on the forum". Its top crash happened only on AMD Ryzen CPUs ([Factorio FFF #231](https://factorio.com/blog/post/fff-231)). Later, "over 12,000 crash reports" arrived automatically for one version ([FFF #285](https://www.factorio.com/blog/post/fff-285)). Factorio still asked for forum reports, because automatic logs carry no reproduction steps and no save.

For Godot in 2026, **Sentry is the only major crash service with an official Godot SDK**. It is MIT-licensed, needs Godot 4.5+, covers Windows and Android with GDScript backtraces, and has a free plan of 5,000 errors per month for one user with 30-day retention ([sentry-godot](https://github.com/getsentry/sentry-godot); [Sentry pricing](https://sentry.io/pricing/)). It throttles repeats by default (at most 5 events per frame, an identical error at most once per second) and includes a ready-made player feedback form that attaches a screenshot ([Sentry options](https://docs.sentry.io/platforms/godot/configuration/options/); [feedback](https://docs.sentry.io/platforms/godot/user-feedback/)). Its costs are real for a beginner. Android export requires Godot's Gradle build ([Sentry Android](https://docs.sentry.io/platforms/godot/configuration/android/)), which means installing a full Android build setup. And because Sentry captures errors through a Logger, **in a release export it will mostly see `push_error` calls, engine errors and native crashes, not the silent script errors** described above. That inference comes from source reading and has not been tested. Firebase Crashlytics is free but reaches Godot only through a community plugin for Android and iOS, without automatic GDScript error capture ([godot-x/firebase](https://github.com/godot-x/firebase)). Steam's built-in error reporting is legacy and supports only 32-bit Windows apps ([Steamworks](https://partner.steamgames.com/doc/features/error_reporting)).

Google Play gives a free baseline with no code. If more than **1.09% of daily users hit a crash, or 0.47% hit an ANR** (Android's "app not responding", a frozen main thread), judged over roughly 28 days, Play "may reduce the visibility of your title" and warn on its store page ([Android vitals](https://developer.android.com/topic/performance/vitals)). An 8% threshold also applies per phone model. For an idle game, a long offline catch-up or a big save load on startup is the obvious ANR risk. Godot now publishes native debug symbols for its official Android templates. These files turn a crash's raw memory addresses into readable function names, and uploading them to Play Console with each release makes engine crashes readable for free ([Godot docs](https://docs.godotengine.org/en/latest/tutorials/platform/android/resolving_crashes_on_android.html)). Because most GDScript failures leave the game running in a broken state rather than crashing, Sentry's "errored sessions" figure is a more honest health number than crash-free rate ([Sentry Release Health](https://docs.sentry.io/product/releases/health/)).

Two constraints shape the release workflow. Crash logs count as collected data on Play's Data safety form ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/10787469)). The GDPR basis for sending them is contested: a German law-firm guide recommends opt-in consent ([activeMind.legal](https://www.activemind.legal/guides/telemetry-data/)), while Factorio ships opt-out. Windows file paths contain the player's username, and Sentry's default server-side scrubbing doesn't promise to remove it ([Sentry scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/)), so the game should scrub paths itself before sending. On the delivery side, Play staged rollouts can be halted but **never rolled back**, so a fix is always a new version ([Play staged rollouts](https://support.google.com/googleplay/android-developer/answer/6346149)). New personal developer accounts must run a closed test with at least 12 testers for 14 days before production ([Play testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465)), which doubles as a natural public-test phase. Since review can take days, the only same-day fixes on Android are defensive save loading and a remote **kill switch**: a tiny JSON file on any web host, read at startup, that can switch off a broken feature or show a notice, and is ignored when offline ([bugnet.io, vendor blog](https://bugnet.io/blog/how-to-write-a-killswitch-for-critical-bugs)). Firebase Remote Config (free up to 100,000 fetches a day) or Heroic Labs' Satori are the grown-up versions for when the MMO backend arrives ([Firebase](https://firebase.google.com/docs/remote-config/pricing); [Satori](https://heroiclabs.com/docs/satori/concepts/remote-configuration/)).

## Conclusion

The research changes one assumption that matters for every later decision. In most engines, release builds are "the same game, faster". In GDScript, a release build is **a game that has stopped noticing its own mistakes**. That moves the burden of catching errors in shipped builds from the engine to the project's own explicit checks: `push_error` at checkpoints, validation before each save, and invariant checks that run in every build type. It also explains why outside testers should get debug exports. The project's existing investment in pure, headless-testable simulation code pays off twice here. The same `scripts/sim/` invariants that the random-play test checks can become the save-time guard and, years later, the server-side validator for the MMO. One validator then serves the tests, the save file and the server.

The second insight is that, for a solo developer, the scarce resource isn't tooling but attention. Every practice that ranks highly below has the same shape: it makes a problem show up by itself, at the moment it happens, with enough context (an id, a seed, a save version) to reproduce it, and without the developer having to go looking. Crash-reporting services, analytics and remote config are the same idea extended to other people's devices. They are worth adding exactly when other people start playing, and not before.

## Recommendations ranked by value per effort

The project already has Logger-based error counting in three headless test scripts (any engine error fails the run). It has `tests/check_project.gd`, which compiles every script, checks data consistency and unknown keys, and enforces the architecture rules. It has `tests/test_invariants.gd`, a seeded random-play test with invariants, away-versus-playing parity and save round-trips. It has atomic save writing with one backup, kept unreadable files, step-by-step migrations, a shape check and removal of unknown content with player notes. And it has the dev panel, gated by `OS.is_debug_build()`. The rankings below build on that. Effort is rough: *tiny* (under an hour with the AI assistant), *small* (a session), *medium* (a few sessions), *large* (a project in itself).

### Now, during Phase 1a

| Rank | What to do | Why it ranks here | Effort |
|---|---|---|---|
| 1 | Add house rules to CLAUDE.md: no silent `if x == null: return`. Every guard logs once with the id involved. Asserts hold only pure checks. `push_error` goes at every trust boundary. A bug gets a test before its fix (Factorio's rule). | It stops the most common AI-code failure mode (silent swallowing) at zero code cost, and makes release builds observable. | Tiny |
| 2 | Create `tests/saves/` and commit `save_v5.json` with the existing `--make-save-sample` option. Add one sample before every `SAVE_VERSION` bump. | The test hook already exists, but no old save is being tested yet. Migrations are the riskiest code for long-lived players. | Tiny |
| 3 | Add a save-time value guard in `scripts/sim/`: reject NaN/infinity in `_is_number()`, check for negative stock, duplicate ids, far-future timestamps and orphan resources or recipes in storage and queues. Repair with a note at load. Refuse to write (keep the last good file, `push_error`) at save. Cover it in `test_simulation.gd`. | It closes the only path by which one logic bug can ruin both the save and its backup within seconds, and it works in release builds. | Small to medium |
| 4 | Space backups out in time: a permanent pre-migration copy, a copy written just before offline catch-up, a first-save-of-session or daily copy, and a protected "before Start over" copy.
